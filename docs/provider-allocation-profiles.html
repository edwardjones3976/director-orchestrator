Z.ai production enrollment (2026-09-27)

The owner enrolled Z.ai as a production lane with an 18% target (owner instruction: "18% target; existing $5 total budget"). The eight earlier lanes' weights were redistributed deterministically, once, and are not silently rebalanced afterwards:

  1. Every nonzero lane was scaled by 82/100 and floored.
  2. The whole points still missing to reach 82 went one each to the largest fractional remainders, ties broken by lane order.
  3. Zero lanes stayed zero; each profile totals exactly 100.

allocation_profiles.redistribute_for_enrollment records the procedure and a test pins it to the literal table above. The pre-enrollment eight-lane targets are kept as PRE_ZAI_ALLOCATION_PROFILES; their digests (pre_zai_allocation_profile_digest) and the older pinned identities still authenticate admissions recorded before the enrollment, in both the PostgreSQL admission ledger and the SQLite engineering journal. They never authorize a new admission, and such rows can never name zai.

The current identity is capacity-allocation-v3-zai-enrollment. As with the 2026-09-08 swap, it changes all four profile digests: an approval bound to an earlier digest does not authorize the new weights, and unfinished plans need a fresh plan and approval. PostgreSQL history recorded under the pre-enrollment digests stays readable, so the workload_history_invalid hold described below does not arise from this change.

Rolling twenty and the normal band of target plus or minus three apply to Z.ai as routing guidance. The owner retired the former target plus five hard limit for Z.ai on 2026-09-27 (as for every other lane on 2026-09-21), so allocation share never blocks its dispatch. The current identity carries no hard tolerance.

The PROPOSED conditional_20260929 profile below was not activated; only its Z.ai target was adopted. No other conditional lane (Grok Bot, VS Code Coding Bot) was enrolled.

Admission and accounting

Assess the prospective last nineteen real assignments plus the candidate using a fixed denominator of twenty, including startup. Normal tolerance is plus or minus three percentage points, an advisory routing preference. The owner retired the rolling-twenty target-plus-five hard ceiling on 2026-09-21 as outdated; the historical ceiling number is preserved for reference and does not block or refuse admission. A zero target remains ineligible regardless of history. Startup under-allocation is warming, never permission for filler work. Engineering targets correspond to about 6.6 OpenAI, 4.2 Claude, 3.6 Z.ai, 2.4 Cursor, 1.6 Grok, and 1.6 Antigravity assignments per full window; these are targets, not mandatory concurrent agents or quotas to fill with unnecessary work.

Reserve admission before provider I/O and retain failed or ambiguous reservations for admission accounting. Accepted productive output and total observed effort remain separate records. Retries and repeated tool calls create no new productive assignment credit. Preserve real history across profile changes and simulate the ordered specialist, producer, and independent reviewer sequence before approval. A profile change invalidates the previous plan approval; it never resets history. Do not silently redistribute shares, relax ceilings, or change an approved provider after failure. Use an explicitly approved feasible fallback profile or return a concise owner decision identifying the unavailable capability.

Previously frozen allocation digests

The 2026-09-08 share swap changes all four profile digests. An approval for the previous digest does not authorize the new weights. Preserve the old plan, prestage packet, admissions, outcomes, and their original digests as evidence. For unfinished work, prepare a new plan and canonical prestage packet under the current profile, then obtain fresh owner approval before dispatch; never edit an old digest in place or reset the rolling history to make a plan pass.

The existing gates distinguish these persisted states:

  • SQLite rejects reuse of the old assignment binding with WorkloadReservationConflict: workload allocation profile binding changed. The engine records OWNER_DECISION_REQUIRED before provider I/O; an existing approval or another attempt key does not authorize rebinding the assignment.
  • PostgreSQL rejects replay of an old admission with workload_admission_identity_changed. Reading prior v3 history under a changed digest, or admitting new work against that history, holds with workload_history_invalid. The original rows remain intact and no provider attempt is inserted.

For the PostgreSQL history hold, keep affected dispatch held and record the old and current profile digests and affected assignment identities for an explicit, reviewed compatibility reconciliation approved by the owner. Fresh plan approval alone does not clear this hold. This change provides no migration or automatic digest rewrite; do not delete, reseed, relabel, or silently accept old history.

Capacity, capabilities, and authority

The owner's account context is OpenAI Pro 20x and Claude Max 5x; other providers are paid but have materially lower capacity. These owner-reported signals inform the approved matrix, not a conversion between providers' usage units. Prefer subscription-backed execution when suitable and authenticated. Separately billed API execution requires its own known budget and gates. Unknown remaining quota, cost, or usage telemetry is unknown, never zero or assumed entitlement.

ChatGPT/Codex is the acting project Director; actual runtime provider identity remains an independently recorded deployment fact. This routing-policy change does not attest deployed provider execution or activate providers, and it does not alter historical attribution. OpenAI production is separately assigned and attributed; Director coordination, Moderator and Participant functions, acceptance supervision, and merge activity do not earn production credit. The materially authoring OpenAI lane cannot review or merge its own candidate; different-provider exact-candidate review remains required. A non-author Director inherits no authorship from delegation, QA, or merge coordination. Reserve a capable different non-author reviewer before production; all exact-SHA, security, CI and owner gates remain binding.

Antigravity is capability-routed within the selected authenticated contract. The restricted fixture contact requires downstream independent verification before integration; the separate team contract requires its explicit grants and host qualification. Allocation grants no exact-SHA acceptance, merge authority, unrestricted context, or broader outbound packet contract. Perplexity receives only explicitly approved public research, never private repository context. Firecrawl and enterprise providers require their actual capabilities, authorized sources, least privilege, authenticated readiness, and supported adapters. A nonzero target is not evidence that a route is operational. GitHub Copilot's production lane is distinct from Copilot Lite hygiene observations; Lite creates no production credit or independent acceptance authority.

The default LangGraph primary OpenAI transport uses the separately billed Responses API. OpenAI Pro 20x does not fund that API route. A native Codex subscription transport is not implemented by this allocation package; subscription capacity is a target-setting signal, not proof of subscription-backed execution.

The default legacy provider registry does not include OpenAI production, Firecrawl, or Copilot production adapters. Their allocation authority is implemented in legacy accounting, but that registry must receive a real authenticated adapter before those lanes can execute there. The LangGraph primary path has its own authenticated transport composition. Microsoft 365 enterprise production remains a typed scope/capability hold in that path until a scoped adapter is supplied.

The legacy default provider registry currently supplies Claude, Cursor, Gemini, Grok, and Perplexity adapters. Its expanded accounting does not add OpenAI, Firecrawl, or Copilot execution adapters; these lanes remain unavailable there unless an actual authorized adapter is composed. The primary LangGraph path uses authenticated transport discovery and scoped capability checks for its new lanes. Neither path infers production readiness from Director credentials or allocations.

Record profile ID and digest, logical lane, actual provider/model/transport, material authors, admission and accepted counts, effort, remaining capacity when known, costs and categorized waste. Token, spend, runtime and concurrency limits remain separate. Missing eligible integration or review capability fails closed; selecting a profile does not install an adapter or deploy LangGraph.

Staged contract constraints and limitations

  • Proposed status only: The descriptor status is PROPOSED. It does not modify active allocation_profiles.py profiles (engineering, mixed, public_research, enterprise), default profile, legacy digests, or any existing assignment bindings. It confers no runtime readiness, admission authority, or enrollment.
  • Descriptive static contract: This module is an immutable static descriptor, not an admission or independence engine. It exposes no eligibility or admission APIs.
  • Activation prerequisites: Eligibility begins on or after 2026-09-29 UTC. Activation requires owner acceptance of Z.ai Lite qualification evidence and a separate, explicit owner activation decision. No automatic Max purchase, activation, or quota redistribution is permitted. All deterministic gates (approval, admission, exact-candidate review, Codex Security, CI) remain mandatory. Prerequisites are named immutable requirements, not runtime status flags.
  • Trial boundary: Z.ai Lite evaluation through 2026-09-28 operates under a separate trial ledger and earns zero accepted-production credit.
  • Policy families and independence: Direct Grok and Grok Bot share the xAI policy family; GitHub Copilot and VS Code Coding Bot share the GitHub/Microsoft policy family. These are owner-selected policy labels for reviewer-independence restriction and anti-duplication; they are not authenticated proof of a managed serving model. Contacts and products remain distinct. A family label never proves reviewer independence, and unknown contacts fail closed.
  • Unresolved integration: VS Code Coding Bot has no identified installed independent integration. Its binding status is unresolved, its route is unbound, and no route is invented. All profile descriptors remain unbound.
  • OpenAI Director-activity floor: At least 75% of OpenAI's own authenticated activity must be Director/control-plane effort. This floor applies to OpenAI's own authenticated work and has a distinct denominator from the 10% direct-production target. This descriptor does not enforce the floor or provide the two activity ledgers; the dual activity ledgers and runtime consumer integration remain required and are not implemented by this contract.
  • Window and tolerance: Evaluated across a 20-slot window (5% per slot), with normal tolerance of +/-3 percentage points (preference). The descriptor's target + 5 points ceiling is a historical reference number only; this staged PROPOSED descriptor was never bound to a runtime cap, and the owner's 2026-09-21 retirement of the rolling- twenty hard-ceiling mechanism removes nothing from it. For Firecrawl (target 1%), a 5% mathematical slot is within that reference ceiling (6%), but this descriptor conveys no actual admission or execution authority.
  • Specialty boundaries: Perplexity public research and Firecrawl authorized retrieval boundaries are preserved; no permanent specialties exist for other participants.
  • Canonical digest derivation: The canonical digest dynamically binds all semantic descriptor fields (effective date, prerequisites, OpenAI floor and denominators, contacts, boundaries) in one immutable payload, ensuring the digest never goes stale.

Contact-family safety (directive #207)

src/director_orchestrator/contact_families.py types every known contact and lane id (for example openai, claude, cursor, grok, grok-bot, gemini, antigravity, perplexity, firecrawl, github-copilot, vscode-coding-bot, zai) to an owner-selected provider-family label: Direct Grok and Grok Bot are one xAI family; GitHub Copilot and VS Code Coding Bot are one GitHub/Microsoft family; Gemini and Antigravity are one Google family. Reviewer-independence checks in review_handoff.py and policy.py::_independent_review_binding_errors reject a reviewer whose provider family matches any material author's family, in addition to the existing identity check, so that separate contact lanes in the same family never create false different-provider review independence or duplicate accepted credit. An identity absent from the table is unknown and fails closed: it is never treated as independent. These family labels are policy labels for independence and anti-duplication decisions; they are not authenticated evidence of which underlying model actually served a request.

Dual activity ledgers

The dual OpenAI activity ledgers (openai_director_activity and openai_direct_production) use schema and kind checks to prevent Director rows from being credited as production within these ledgers. Runtime credit and workload caps are unchanged until a consumer integrates the ledgers. Director/control-plane activity includes intake, planning, decomposition, packet preparation, capability-based routing, team communication, synthesis, acceptance supervision, completion reporting, and owner escalation. Direct-production activity encompasses bounded production assignments authored by OpenAI under ordinary authorship, review, CI and merge gates. The ledgers are distinct, append-only SQLite files. A rolling 7-day observation window looks back from the current moment. A minimum of 20 total valid events must be recorded within that window before history is considered sufficient, and a floor of 75% Director activity must be maintained to avoid a utilization hold. A kind outside the ledger's own kind set is refused (invalid_director_kind / invalid_production_kind) and never recorded.
