4. Stage A switch write

Backup of prior values recorded (§2) ☐. Then write exactly these three, and nothing else:

LANGGRAPH_PRIMARY_ENABLED=true
LANGGRAPH_PRIMARY_NEW_INTAKE_ENABLED=true
LANGGRAPH_PRIMARY_OFFLINE_SIMULATION_ENABLED=true

Left untouched and expected to stay false: LANGGRAPH_PRIMARY_LIVE_PROVIDER_DISPATCH_ENABLED, ALLOW_PAID_RUNS.

Recreate with the compose file that matches the running deployment. A stale docker-compose.yml drops the primary DSN and the /repository bind with no warning beyond an orphan-container notice.

The first two switches must move together: ENABLED=true with NEW_INTAKE_ENABLED=false returns HTTP 503 on every intake, with no per-request fallback — the flag is read once at import.

7. Operational findings from A-16 (public research, Director-side surface)

Recorded as untrusted public evidence, evaluated by the Director. It is not evidence that the repository Firecrawl lane is enrolled or live.

  1. thread_id has a bounded column length. LangGraph's Postgres savers store thread_id in a limited-length column; values over 255 characters produce a database error. Deterministic IDs should be UUIDs or hashes rather than concatenated descriptive strings. Check the Director's generated thread IDs against that bound before the first long-running task.
  2. Checkpoints grow without bound. Safe pruning is an open feature request upstream (langgraph#8531), not a shipped capability — the proposed keep_latest would retain the newest checkpoint per (thread_id, checkpoint_ns). Until it exists, the primary database grows monotonically. Plan backup sizing and disk headroom accordingly, and do not assume a retention policy exists.
  3. (thread_id, checkpoint_ns) is the isolation key. This matches the deployment's per-profile checkpoint namespace design, and it is why a distinct LANGGRAPH_PRIMARY_CHECKPOINT_NAMESPACE per profile is load-bearing rather than cosmetic — two profiles sharing a namespace would share checkpoint rows.

Checked against this source, 2026-09-09

Finding 1 verified, and it is not a live defect. thread_id is composed as f"{namespace}:{task_id}" (langgraph_primary.py:2188, and identically in langgraph_shadow.py:697). At real configured values:

Profile namespace task id composed headroom to 255
deployed default-director-primary-v1 27 17 45 210
proposed sim sim-director-primary-v1 23 17 41 214

With this task-id shape a namespace could reach 237 characters before the bound is at risk, so current values are safe by a wide margin.

But there is no length validation on the composed value anywhere in the source. An operator who sets a long checkpoint namespace gets a database error at runtime rather than a configuration refusal at startup. Recorded as a latent robustness gap for the follow-on, not a blocker: a configuration_valid check on len(namespace) + len(task_id) + 1 <= 255 would convert a runtime failure into a startup refusal, which is the behaviour every other switch in this configuration already has.

Finding 2 also verified. A search of the source for pruning, retention, keep_latest, or any checkpoint deletion returns nothing. The upstream gap applies here unmodified: the primary database grows monotonically. Size backups and disk headroom on that basis, and do not assume a retention policy exists to be tuned.

9. What this worksheet does not establish

A completed Stage A pass proves that the primary plane owns intake and runs its own lifecycle with the money switched off. It proves nothing about live provider execution, and its provider results are produced by in-process doubles. It satisfies Gate 3 and supplies evidence toward gates 2 and 6 for the ledger to record, closes no other gate, and leaves eight of nine outstanding, Gate 8 among them at F. Do not describe it as an activation.
