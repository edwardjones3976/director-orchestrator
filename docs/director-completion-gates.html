Director Completion Gates

Status: Production-capable isolated worker runtime; default off; no completion authority Schema authority: director-gate-ledger/v1 and director-gate-result/v1 Frozen starting point: 21c4c70ad4bb1135e82d7b69df9866a1634f3546

Purpose

Director Completion Gates define immutable, provider-neutral evidence contracts for substantial assignments. They record what must be observed before work begins and what a producer or independent reviewer actually observed at an exact commit.

Gate evidence supplements the existing work/result packets, independent exact-SHA review, Codex Security, trusted CI, and deterministic merge policy. It never grants assignment, provider-selection, budget, repository, approval, review, merge, deployment, LangGraph, provider-dispatch, or external-write authority.

The runtime foundation adds deterministic semantic validation, append-only gate and worker SQLite stores, a fixed-argument runner registry, bounded shell=False execution, aggregate gate-evidence reporting, and a fail-closed readiness surface. Production worker construction requires three independent choices: gate evidence, isolated proof, and worker execution. It accepts only ISOLATED_PROOF_LANE ledgers. It is not wired to provider dispatch, external writes, merge, deployment, or project-completion authority.

Two different authorities

Aggregate gate_evidence_complete means only that every current required gate has authenticated PASS evidence at the current exact head.

assignment_acceptance_authorized is an assignment-scoped claim. It is true only when gate evidence is complete and at least one required gate carries INDEPENDENT_REVIEWER evidence from a principal who is not a material author. That is the strongest statement one assignment ledger can make about itself.

project_completion_authorized is always false in the per-ledger aggregate. Project completion spans multiple assignments and depends on authorities the gate store does not hold. aggregate_project_completion_eligibility answers that question separately and fails closed unless every declared assignment reached assignment acceptance and every one of these is supplied as authenticated evidence by the caller:

  • independent_exact_sha_acceptance
  • codex_security
  • trusted_ci
  • deterministic_merge_policy
  • deployment_or_product_acceptance_when_applicable

Assignment acceptance never widens into project completion. merge_eligibility re-checks this and refuses any evidence bundle that claims otherwise.

Configuration

Both switches default off and both fail startup closed when enabled without an isolated store:

Setting Effect
COMPLETION_GATES_ENABLED Records durable gate evidence
COMPLETION_GATE_ISOLATED_PROOF_ENABLED Additionally permits runner execution
COMPLETION_GATE_STORE_PATH Must be a distinct file from SQLITE_PATH and every LangGraph shadow or runtime database
COMPLETION_GATE_RESULT_MAX_AGE_SECONDS Result freshness ceiling (1–2592000)
COMPLETION_GATE_WORKERS_ENABLED Constructs the explicitly selected worker tiers; defaults off
COMPLETION_GATE_WORKER_STORE_PATH Append-only worker reservations/events; must be distinct from every other database
COMPLETION_GATE_EXECUTION_TIERS container for the currently activatable production worker; defaults to container
COMPLETION_GATE_HOST_BROKER_PATH Reserved for the audited-host tier, which remains fail-closed until its OS controls can be independently verified
COMPLETION_GATE_CONTAINER_RUNTIME_PATH Existing absolute path to the container runtime executable when container is selected
COMPLETION_GATE_CONTAINER_IMAGE Immutable name@sha256:<64 lowercase hex> image required by the container tier

/health reports these as booleans under completion_gates, including a permanently false completion_authority.

Construction is not activation or authority

The normal API startup path now constructs the worker registry, append-only worker store, and selected backends when—and only when—all three execution switches and every selected-tier binding validate. Health distinguishes:

  • configured evidence recording;
  • isolated-proof contract enablement;
  • worker execution enablement;
  • executor construction;
  • per-tier backend readiness; and
  • the permanently false completion-authority claim.

The implementation is therefore production-capable, but a repository merge does not activate it. The deployed environment must supply the explicit switches, distinct database, executable fingerprints, and immutable image, and must then show worker_execution_ready=true. No public raw-command endpoint or automatic gate scheduler is introduced. An authenticated internal caller must still supply the exact ledger, gate, task, assignment, head, registry, worker-spec, and idempotency bindings.

One worker job identity has one durable reservation. A successful redelivery replays the stored outcome; a backend exception becomes RECONCILIATION_REQUIRED and is not automatically redispatched. This worker lane produces evidence only. It cannot become a second provider dispatcher, task-state writer, GitHub/Slack writer, merger, deployer, or project-completion authority.

Windows worker processes are created suspended, assigned to a mandatory kill-on-close Job Object, and resumed only after assignment succeeds. POSIX workers run in a separately owned session. Both tiers launch from an OS-owned neutral directory rather than repository-controlled current working data. Orchestrator-account Git probes use that same neutral directory and pass the repository only through git -C <repository>. The legacy direct runner refuses Python -m profiles; module-based validation runs only through an isolated host-broker or disposable-container worker so repository modules cannot shadow the selected standard-library module. The audited host-broker contract receives the repository path explicitly and a literal --env PYTHONPATH=<repository>/src argument; it must apply that value inside its low-privilege sandbox without shell interpretation.

The disposable-container backend always supplies PYTHONPATH=/workspace/src and redirects bytecode caches to the /tmp tmpfs. The shipped bare Python image is registered only for dependency-free compileall; unit tests and pip check remain audited-host specs until a separately reviewed dependency-bearing image is configured. Every container has a deterministic job-bound name and label. After every CLI outcome—including timeout, overflow, or ambiguity—the runtime authenticates the Docker executable, forces removal only when the label matches, and verifies daemon-side absence. Absence must remain stable across two consecutive reads in a bounded poll, so a late daemon-side creation cannot satisfy cleanup with one transient negative read. Unverifiable cleanup becomes reconciliation-required evidence, never success.

Applicability

The Director should propose Completion Gates for medium-or-higher complexity, multi-component work, long implementations, new dependencies or persistence, recovery/concurrency/idempotency changes, security boundaries, cross-platform validation, external-effect boundaries, LangGraph/provider/merge-gate work, or an owner request for exhaustive completion discipline.

Factual replies, formatting changes, spelling corrections, one-line safe edits, trivial fixtures, and the existing bounded minimal-integration-fix procedure do not receive a gate ledger unless their scope or risk expands.

Companion-contract boundary

The accepted model-work-packet-v1 and model-result-packet-v1 contracts remain unchanged. Completion Gates are companion documents:

  • director-gate-ledger/v1: Director-issued immutable gate definitions.
  • director-gate-result/v1: one immutable observation attempt for one gate.

Authoritative runtime instances live in a separate append-only, Director-controlled SQLite evidence store, outside canonical task tables, repository fixtures, and LangGraph checkpoint storage. Checked repository examples still prove only the contract; they never become authoritative store records.

Immutable ledger lifecycle

An issued ledger is never edited in place.

  1. A PLANNED revision has expected_head_sha: null.
  2. A producer may propose additional gates but cannot edit either gate array.
  3. The Director may adopt those proposals only by issuing a successor ledger with a new ledger_id, incremented ledger_revision, and predecessor_ledger_digest.
  4. When implementation returns, the Director issues a HEAD_BOUND successor whose expected_head_sha is the exact candidate SHA and whose candidate_result_digest binds to the producer result that supplied it. The successor also records every authenticated material_author.
  5. A new commit requires another successor and invalidates all gate, review, security, CI, and merge evidence bound to the old head.

ledger_series_id links immutable revisions. Revision 1 has no predecessor and must be PLANNED; a HEAD_BOUND ledger must be revision 2 or later with a predecessor. Old-head evidence is retained immutably but is ineligible for current completion. A PLANNED ledger cannot yield a result eligible for aggregate completion; eligible results bind to the current HEAD_BOUND ledger whose expected head equals the executed SHA. Cross-document lineage, equality, and monotonicity are deterministic semantic checks scheduled for the models/binding increment; JSON Schema alone cannot authenticate them.

Gate ownership

director_gates and producer_added_gates are separate arrays.

  • Director gates are mandatory policy evidence unless the Director originally classified one as advisory.
  • A producer may propose additional required or advisory coverage.
  • Producer additions cannot remove, replace, waive, reorder, rename, or weaken a Director gate.
  • A producer proposal becomes authoritative only when the Director issues a new immutable ledger revision containing it.
  • Once adopted as REQUIRED, a producer-added gate is as completion-blocking as a required Director gate, but it still cannot weaken a Director gate.
  • Self-declared author fields are provenance data, not authentication.

director_gate_set_digest independently binds the ordered Director gate array; producer_gate_set_digest binds the ordered adopted-proposal array. The ledger digest changes when any gate, ordering, requiredness, path, runner binding, dependency, abandonment rule, author, or expected head changes.

Every applicable ledger must contain at least one REQUIRED Director gate. An empty required set is never vacuous success; the runtime aggregator fails closed unless schema validation and semantic binding establish that invariant.

Gate kinds

Runnable

A runnable gate selects an allowlisted runner_id, a pinned runner-definition digest, a pre-registered parameter-profile ID and digest, a repository-relative working directory, expected exit code, structured output matcher, timeout, output ceiling, risk classification, dependencies, and abandonment policy.

There is no raw command, shell string, or free-form argument array. The isolated runner resolves the exact argument vector from an authenticated runner/parameter-profile registry, rejects unknown bindings, and uses shell=False with a minimal inherited environment.

repository_owned_script additionally binds a repository-relative path and exact Git blob SHA. Changing that script requires a new ledger and fresh approval.

Manual

A manual gate describes the eligible evaluator roles, independence requirement, and human or provider evidence required. It is not an executable runner and cannot carry executable, argument, or working-directory fields. A manual PASS must bind an authenticated evaluator, exact artifact/head, clean review state, and evidence digests. The semantic validator derives evaluator eligibility by intersecting the authenticated actor roles with the gate's eligible_evaluator_roles; the result's evaluator_eligible boolean is only a consistency assertion and cannot grant a role.

Manual evidence enters the Director's authenticated sanitization pipeline before persistence. Raw claims and locations are never stored. Each evidence item stores only sanitized_claim and sanitized_location, their reproducible digest, the authenticated sanitization-record digest, redaction/scanner identities and digests, and post-redaction findings. A manual PASS requires passed redaction and secret scanning with no retained findings. The semantic validator must read back the sanitization record and authenticate the configured redactor and scanner; self-asserted scan fields are not completion evidence.

External CI

An external-CI gate binds a repository, workflow path, workflow blob SHA and definition digest, required check name, and trusted GitHub App identity. A result also binds run, suite, and check IDs, exact observed head, terminal conclusion, completion/retrieval times, and authenticated API readback. It observes existing CI only: this contract does not authorize triggering CI. It is not a provider-executed runner and not acceptance by itself.

Digest rules

All contract digests use RFC 8785 canonical JSON and lowercase SHA-256 with the sha256: prefix. The exact construction is SHA-256(UTF-8(domain) || 0x00 || RFC8785(value)).

  • gate_definition_digest: domain director-gate-definition/v1; canonical gate object with only that field omitted.
  • director_gate_set_digest: domain director-gate-set/v1; canonical ordered Director gate array, including each gate-definition digest.
  • producer_gate_set_digest: domain producer-gate-set/v1; canonical ordered adopted producer gate array, including each gate-definition digest.
  • ledger_digest: domain director-gate-ledger/v1; canonical ledger object with only that field omitted.
  • result_digest: domain director-gate-result/v1; canonical result object with only that field omitted.
  • sanitized_excerpt_digest: domain director-gate-sanitized-excerpt/v1; canonical JSON string value of decisive_output.
  • sanitized_text_digest for manual evidence: domain director-gate-sanitized-manual-evidence/v1; canonical object containing only sanitized_claim and sanitized_location.
  • sanitization_record_digest: domain director-gate-sanitization-record/v1; canonical object containing the sanitized-text digest, pipeline source, redaction status/identity/digest/counts, and secret-scan status/identity/digest/counts.
  • artifact_binding_digest for manual evaluation: domain director-gate-manual-artifact-binding/v1; canonical object containing the repository, gate ID/definition digest, expected and executed SHA, worktree before/after SHA, authenticated principal, and provider run reference.

Every other field remains inside its digest, including timestamps, expected head, origin, requiredness, registry identity, dependencies, abandonment, environment, redaction, and reverification data. Digests detect mutation; they are not signatures and grant no authority.

Result meaning

One result document represents one immutable attempt for one gate. It binds:

  • task, assignment, work packet, authority snapshot, ledger revision and digest;
  • gate ID and gate-definition digest;
  • exact executed SHA, every material author, and an authenticated evidence actor;
  • producer or independent-review role;
  • timestamps, clean-worktree evidence, environment, and exact runner resolution where applicable;
  • sanitized decisive output, status, and reverification lineage.

Evidence-actor identity is separate from resolved-runner identity. A provider, human evaluator, or trusted external-CI principal cannot be represented as a runner. A runnable result binds the runner registry/version/digest, definition and implementation digests, executable fingerprint/version, canonical argument-vector digest, and sanitized-environment profile digest.

ABANDONED requires a permitted reason code, authenticated actor, timestamp, attempt count, last evidence, lost coverage, and one of BLOCKS_ACCEPTANCE, OWNER_DECISION_REQUIRED, or RESHAPE_REQUIRED. It is honest terminal evidence for that attempt and never acceptance. FAIL, BLOCKED, and ABANDONED never contribute to aggregate completion. Aggregate completion is derived only when every current required gate has a matching PASS on the same HEAD_BOUND ledger and exact SHA. Even then, independent acceptance, Codex Security, trusted CI, and deterministic merge policy remain separate.

The full_output_digest uses the domain director-gate-sanitized-output/v1 and commits to complete sanitized streams before persistence truncation. Its byte payload is "stdout\0" || uint64be(stdout_length) || stdout_utf8 || "stderr\0" || uint64be(stderr_length) || stderr_utf8. Results record captured, persisted, and omitted byte counts, the output ceiling, truncation, sanitized decisive excerpt and digest, redaction/scanner identities and digests, counts, and categories. Raw output is never persisted or hashed by this contract. Both redaction and secret scanning must cover every persisted text field and pass before a result can be PASS; the post-redaction secret finding count and categories must be empty. Captured, persisted, and omitted byte counts describe sanitized bytes. The semantic validator must prove stdout + stderr = total, persisted + omitted = total, persisted <= ceiling, and that truncated exactly matches whether bytes were omitted. It must also derive exit_code_matches_expected from the observed exit code and the ledger's expected exit code, derive expected_output_match by applying the ledger matcher to decisive_output, require the result output ceiling to equal the ledger limit, and recompute the sanitized-excerpt digest. Result booleans never substitute for those comparisons.

Schema validity is not completion eligibility

Every result declares director-gate-result-semantic-binding/v1, but that value is not self-authenticating. The deterministic validator loads the authenticated current ledger and proves all of the following before append or aggregation:

  • task, assignment, work packet, authority snapshot, repository, ledger series, ledger ID/revision/digest, gate ID/type/definition digest, and expected/executed SHA all match;
  • resolved runner, registry, runner definition, parameter profile, implementation, working directory, and script/CI workflow identities match the gate and ledger;
  • worktree before/after heads equal the expected head, and CI repository, workflow, trusted app, check name, and observed head equal their authenticated bindings;
  • the evidence actor and provider run/readback are authenticated, and an independent reviewer is absent from every material-author record;
  • manual evaluator eligibility is derived from authenticated actor roles and the selected gate's role allowlist, and manual text is bound to an authenticated sanitization record before persistence;
  • dependencies reference current-ledger PASS result digests; and
  • output digests, byte arithmetic, redaction, scanning, and abandonment policy are internally and cross-document consistent.

A schema-valid document that has not passed that validator is untrusted data and cannot contribute to completion, review, security, CI, merge, deployment, dispatch, or any other authority decision. The append-only store accepts only validator output bound to separately authenticated readback context. The reference assertions require evaluator roles and sanitization-record digests from an authenticated Director-controlled readback supplied separately from the result document. The result's role list, scan booleans, and record digest are consistency assertions only and cannot authenticate themselves. Manual artifact-binding digests are likewise recomputed and must appear in a separately supplied authenticated readback. exact_artifact_verified cannot make an otherwise unbound review authoritative.

Isolated runner boundary

Structured host execution is permitted only through an exact-fingerprint, separately installed low-privilege broker. The Director passes a registered launcher profile and fixed argv; it never invokes a repository command directly under the orchestrator account. The broker contract requires no network, a read-only repository view, bounded CPU/memory/PIDs/output/time, and complete process-tree termination. A missing or changed broker fingerprint fails startup or execution closed.

The disposable-container tier requires an immutable image digest and a fixed argv. It uses no network, a read-only root, a read-only repository bind mount, a bounded tmpfs, a numeric non-root identity, no capabilities, no-new-privileges, and bounded CPU/memory/PIDs/output/time. Neither tier accepts a shell string, request-supplied argv, an externally writable mount, or ambient credentials.

Worker stdout and stderr are not retained as prose. The production sanitizer discards both streams and emits only a closed-vocabulary marker plus a domain-separated content digest of the discarded streams. Regex is therefore not the privacy boundary.

For a containerized Director, do not mount the host Docker socket or a writable host control surface merely to satisfy worker readiness; that would expand the orchestrator's privilege boundary. Activate the container tier from a dedicated local Director service account that can reach the container runtime, or keep COMPLETION_GATE_WORKERS_ENABLED=false until a separately authenticated worker service is deployed. The audited-host tier is intentionally not activatable until the Director can independently verify its low-privilege identity, network policy, resource limits, and read-only repository handle. Health reports disabled workers as not constructed, never as a silent fallback.

An authenticated registry may register fixed profiles for:

  • python_unittest
  • python_compileall
  • pip_check
  • json_schema_validate
  • compose_config
  • container_build
  • git_diff_check
  • secret_hygiene
  • powershell_parse
  • repository_owned_script

github_trusted_ci and manual_review remain non-runnable gate kinds.

The isolated runtime rejects unknown runners, shell strings, parameter-profile or argument injection, directory escape, symlink/hard-link escape, wrong repository/worktree/SHA, credential inheritance, unbounded execution/output/regex, stale evidence, and non-atomic writeback. Sanitized process execution is not a complete sandbox; containers or disposable environments are required when stronger isolation is needed.

Semantic checks enforced beyond JSON Schema

The deterministic validator and store enforce:

  • unique gate IDs and order values;
  • dependency existence, ordering, and acyclicity;
  • ledger revision/predecessor lineage;
  • cross-document task, assignment, digest, gate and SHA equality;
  • producer additions being monotonic;
  • authenticated Director issuance and provider identity;
  • evidence actors differing from every material author for independent review;
  • repository realpath, symlink and hard-link containment;
  • result freshness and atomic evidence persistence.

Canonical repository identities and repository-relative paths reject dot components, .git, Windows device/alternate-stream syntax, absolute paths, backslashes, repeated separators, and trailing separators. Runtime execution also proves the current Git head and realpath containment. Repository-owned scripts add exact Git-blob/content binding plus symlink/hard-link rejection.

The hardened runner, provider handoff, Slack status, pilots, and promotion metrics remain later independently reviewable increments.

Default-off and rollback rule

No Completion Gate worker executes unless gate evidence, isolated proof, and the separate worker switch are all enabled for a named ISOLATED_PROOF_LANE assignment. Every selected tier must also pass executable authentication and store-isolation readiness. Defaults remain off. No global Unlazy installation, Claude Stop hook, ambient shell execution, production credential, external write, deployment, or LangGraph writer connection is authorized here.

Disabling either proof flag stops execution without deleting immutable evidence. Removing the isolated runtime modules and their separate SQLite database rolls the foundation back without changing canonical task or LangGraph state.

Worker graduation

Before enabling workers for a named profile:

  1. independently accept the exact implementation SHA after trusted CI and security review;
  2. prove the gate and worker stores are distinct from task, shadow, runtime, runtime-ledger, and resume-claim stores;
  3. authenticate the host broker and container runtime executable fingerprints;
  4. pull and verify the exact container image digest without granting the Director a host Docker socket or writable host-control surface;
  5. run one fixed no-write profile in each selected tier and prove exact head, clean worktree, no network, resource bounds, process-tree termination, output withholding, and append-only replay;
  6. restart after reservation and prove the stored outcome replays without another execution; then inject one ambiguous backend outcome and prove it stops for reconciliation; and
  7. record the profile, exact SHA, registry/spec digests, safe store identity, health result, and rollback evidence before widening use.

Worker rollback

Stop new gate execution, set COMPLETION_GATE_WORKERS_ENABLED=false, and restart. Confirm executor construction and worker execution readiness are false while gate evidence remains readable. Do not delete or alter RUNNING, terminal, or reconciliation-required reservations to manufacture a retry. After all worker jobs are terminal, the isolated-proof and evidence switches may be disabled independently. Preserve both append-only stores; deleting them is not rollback of an execution or external effect.
