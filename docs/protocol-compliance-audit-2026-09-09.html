Protocol compliance audit — the 2026-09-13 delivery

Auditor: Claude, acting Director-Orchestrator · 2026-09-09 Scope: the delivery documents and work orders on branch claude/activation-plan-2026-09-13, checked against AGENTS.md, docs/team-operating-charter.html, docs/contribution-attribution-policy.html, docs/provider-capacity-and-authority.html and the deterministic policy.

This is the Director auditing its own submission. It is not independent review and does not substitute for it. Every claim below names how it was checked.

1. Antigravity credential — resolved without generating anything

The owner asked whether an Antigravity key exists or must be generated. It exists. No browser was opened, no credential was minted, and no secret value appears in any document, transcript or commit.

Fact Evidence
GEMINI_API_KEY is set in the deployment environment file presence and length only; value never read into output
The primary transport auth map accepts exactly {GEMINI_API_KEY, GOOGLE_API_KEY} for the antigravity lane primary_transports.py:150
A second key is provisioned for the edge-oracle profile same check on .env.edge-oracle
GEMINI_AGENT = antigravity-preview-05-2026, GEMINI_DAILY_BUDGET_USD = 5.00 deployment environment file
.env.uppercut holds a one-character GEMINI_API_KEY — a placeholder, not a key flagged only; different project, not this delivery

gemini_supplemental_readiness evaluated against the deployment environment and the configuration defaults returns true on all eleven checks: credential_configured, agent_configured, usage_model_configured, usage_retry_attempts_valid, usage_retry_delay_valid, token_budget_valid, daily_budget_valid, daily_request_limit_valid, subordinate_mode, review_verdict_disabled, primary_authority_disabled.

Three of those pass on configuration defaults rather than explicit settings — usage_model_configured, daily_request_limit_valid and subordinate_mode. They are correct today, but a default is a weaker guarantee than a written value. Recommendation: write GEMINI_USAGE_MODEL, GEMINI_DAILY_REQUEST_LIMIT and GEMINI_MODE=antigravity_subordinate explicitly into the profile so the subordinate constraint is recorded rather than inherited.

LANGGRAPH_PRIMARY_ANTIGRAVITY_TEAM_ENABLED is absent and therefore false. The credential was never the obstacle to team mode; the open question remains D-14, whether a reachable, authenticable pinned SSH worker host exists.

Why no key was generated. Minting one through the browser would have put a live secret into a page render and a conversation transcript, and creating a credential is an owner-reserved action under rule 10. It was also unnecessary.

2. Contribution attribution — one real defect, found and fixed

Checked directly against contribution_tags.py rather than by inspection.

Condition Result
First nonblank line after any reserved header is a BEGIN tag PASS, all four documents
Last nonblank line is an END tag PASS, all four
Outer BEGIN/END contributor, system, date and time match exactly PASS, all four
The submission diff adds that exact pair PASS, all four
No inline tag in a syntax-sensitive format PASS — no JSON, JSONL, CSV or lock file was authored

The defect. The activation plan was changed across four commits and the delegation matrix across three, each still carrying only its original outer pair. The policy requires a fresh outer pair on every safely commentable file changed in the current submission, with earlier records preserved. Evaluated as one submission the branch passes; evaluated per commit those two files would be rejected. Both now carry a fresh outer pair with the earlier records nested inside, verified after the fix.

A note on the checker run. An earlier invocation of scripts/check_contribution_tags.py reported errors on all four documents. That run was environmentally invalid — it was executed from one worktree with GIT_DIR overridden to a different repository — and its output is not a verdict either way. The conditions above were therefore checked directly against the module. The authoritative run belongs to CI on the pull request, and the Director does not claim to have passed a gate it did not validly execute.

8. What this audit does not establish

It does not establish that any provider route is enrolled, authenticated or live. It does not substitute for independent exact-SHA review, trusted CI or security review, none of which the Director may perform on its own submission. It does not attest that the deployment's runtime state matches its configuration — that remains the open WO-01 health read. And it is a self-audit: the lane that wrote the documents also checked them, which is exactly the arrangement the acceptance rules exist to distrust.
