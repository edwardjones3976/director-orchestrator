Responses and team readiness composition

DefaultPrimaryActivation's constructor-created preflight_parallel_assignment callback is the readiness gate PostgresParallelDispatch.reserve_ready calls, under its own locked transaction, for every reservation-eligible assignment in a wave before that wave's ACTIVE rows exist. It predicts eligibility only: it performs no HTTP, provider launch, spend/usage insert, workload admission or STARTED event. A hold records paid_setup_required and leaves the assignment PENDING.

Readiness

check_budget_setup/check_team_setup (primary_paid_preflight.py) validate the signed budget or grant - signature, UTC day, ceilings - on the caller's own connection. For Responses with an enrolled meter, the real OpenAIResponsesPacketTransport.preflight additionally runs EnrolledResponseMeter.preflight_binding: signature, validity interval and exact enrollment/context binding, with no HTTP, no input-token counting and no database reservation. prepare() keeps that reservation check for actual dispatch. Neither branch probes query_factory, worker_factory, TeamAuthority.authorize or admissions. Readiness canonicalizes the packet with packet_contracts.canonical_json_bytes (RFC 8785) - the same bytes real dispatch sends and a signed enrollment's work_packet_digest was computed against.

The selection

Readiness records one ReadinessSelection per assignment: provider, exact packet digest, roster, signed authority digest, writer fencing generation, enrolled document digest, authority day, and one absolute deadline shared by every attempt of that roster. It is re-proved at four points, in this order: before admission opens a transaction, after admission's own locks and before its COMMIT (revalidate_selection), immediately before provider I/O, and inside the transport that resolves the meter. A changed packet, a writer takeover, a replaced enrollment registry, or an authority that no longer resolves to the checked one is a different selection and fails closed as a WorkloadAdmissionHold - which execute_ready maps to OWNER_DECISION_REQUIRED - with nothing admitted. A selection this process no longer holds (a restart between reservation and dispatch) also fails closed, before either database call: the lookup's absence raises immediately, so a known refusal never reads the writer or persists a packet artifact on the way out - and never runs those calls with the None deadline that absence implies. It is never re-derived.

Two of those points matter because waits happen between them. The ledger repeats the authority comparison inside the authoritative locked admission via expected_authority_digest, so a valid admission object for some other authority is refused before any monetary, workload or STARTED row is written. revalidate_selection runs after the admission transaction has finished waiting on its locks and before the STARTED insert. It is handed that transaction's own connection, so it re-runs the authority selection itself - select_budget_authority/select_team_authority, the same uniqueness, signature, revocation, grant/packet binding and UTC-day rules readiness applied

  • without acquiring a second pooled connection while those locks are held. The read-only spend ceilings are deliberately not repeated there: this attempt's own reservation is already inserted, and counting it twice would refuse a correctly funded attempt. The writer lease is re-proved at the same point, and the enrollment document is compared again. A competing authority registered while admission waits therefore rolls the monetary, workload and STARTED writes back together.

The writer generation is bound to the writer admission actually resolves, not the one dispatch read when it began. The live coordinator resolves - and renews or, after an expired lease, reacquires - the task writer at the moment it enters admission, and a reacquired lease carries a new fencing generation. An independent real-PostgreSQL probe expired the lease after the real authority lookup and before that resolution: readiness had selected generation 1, dispatch had captured generation 1, so the comparison between those two passed while admission committed under generation 2, leaving a STARTED attempt, a spend row, a workload row and a constructed HTTP client behind. The coordinator now receives the generation the selection was checked under (expected_writer_generation) and refuses a resolved writer of any other generation (readiness_writer_changed_before_admission) before the admission transaction is entered, so nothing is written and no provider client is constructed. The reacquired lease itself stands: a new generation is a different selection, not a renewal.

OpenAIResponsesPacketTransport.send then compares the enrollment it actually resolved against the carried enrollment_digest, so a registry substituted after the caller's own comparison - or a meter lost entirely - cannot reach the provider.

Authority at the real generation boundary

The Responses transport counts input tokens before it generates anything. That count is itself a provider request: it is bounded by the same carried deadline as the rest of the attempt (remaining_seconds() is re-evaluated for it and the whole call runs under asyncio.timeout), but within that bound the provider can make the caller wait, and every check above ran before that wait. ProviderAdapterContext.authority_recheck

  • created by the live coordinator, never by a transport - is therefore called immediately before the generation request and re-reads the durable rows: the wave's kill_switch (what coordinator.cancel engages), this task's langgraph writer lease, owner token and fencing generation, this assignment's ACTIVE reservation binding, and this attempt's own latest event. A cancellation, a writer takeover, an expired lease, a changed plan binding or an already reconciled attempt during the count stops the request. The refusal is a WorkloadAdmissionHold, so the roster propagates it as an owner decision instead of an ambiguous paid dispatch: no generation request is made, no automatic repeat follows, and the admitted rows, slot and any recorded usage are preserved. A transport with no such callback holds no authority of its own and invents none.

A WorkloadAdmissionHold propagates out of _execute_three_attempt_roster instead of being classified. For a provider transport it arises before the real request: before adapter.dispatch is entered at all, or from authority_recheck inside the Responses path, after the input-token count and strictly before the generation request. An earlier revision of this document said it was never raised after a generation request; that was wrong for the native team lane, whose callbacks run the same recheck after native execution - at each local-command boundary and immediately before candidate integration - so a generated result may already exist when the hold is raised. The classification is unchanged because it is still correct: the attempt's durable STARTED row remains, admission refuses to redispatch a STARTED attempt until it is reconciled, and the hold is propagated as an owner decision with the admitted rows, slot and evidence left as they are. Nothing is replayed and nothing is recorded as an AMBIGUOUS paid outcome on a guess.

The team lane

NativeTeamPacketTransport now consumes the same two things the Responses lane does. context.deadline is the primary lane's remaining budget: it bounds every SQL acquisition, statement and transaction this transport opens (through bounded_transaction), refuses an already-spent bound before the worker is prepared, and is handed to a worker that declares accepts_primary_deadline so preparation and the remote exchange narrow their own grant timer instead of restarting a full one each. context.authority_recheck runs inside before_execute - after preparation has waited, immediately before the execution entitlement and any native run - at each local-command boundary, again immediately before the durable candidate is integrated, and once more inside the integrator's own transaction, on its connection, after it holds the writer row and before it writes any Git object. That last read is the one that matters against a same-owner cancellation: engage_kill_switch locks the same writer row before committing its switch, so a cancellation that completed before the integrator's lock is seen there and refused (wave_cancelled_before_candidate) with no candidate object, retention ref or row created, while one still waiting behind the lock is serialized after the candidate rather than racing it. The transport's read a moment earlier ran in a separate transaction and could not see that ordering. Work after the exchange spends this operation's one completion allowance rather than a fresh budget, and a failure there is refused conservatively: the capture the transport already stored and the STARTED attempt remain, and nothing is retried.

A standalone caller carries neither value; every one of these checks is then a no-op, and a worker that declares no support keeps its previous call signature unchanged. When a primary bound does exist, a worker that cannot enforce it is refused before it is invoked, rather than being held to nothing while the wave believes it is bounded.

The decisive recheck is after the blocking work, not before it: claiming the execution entitlement takes a pooled connection, a query and row locks, so the authority is re-read once that returns, with nothing between it and the worker being told to execute. The local-command boundary does the same.

Across hosts the bound travels through a causal anchor handshake, never as this host's time.monotonic() instant, which means nothing on another machine; never as a remaining duration re-anchored on arrival, which an earlier revision used and which hands the transit back; and no longer as a UTC instant, which the previous revision used and which only bounds the remote side under a clock-agreement premise this protocol cannot establish - an independent probe showed a receiver clock fifteen seconds behind, masked by ten seconds of transit, passing the plausibility check and running five seconds past the director's bound. The remote server now speaks first: it takes an instant on its own monotonic clock, then sends an authenticated anchor frame carrying a token it generated, bound to the challenge. The director samples what is left of its fixed bound only after that frame has arrived and sends it in prepare together with the token. The server's instant precedes the director's sample in real time, so anchor + remaining can only be early - by at least the transit in each direction and any pause on either side - and never late; it is never receipt + remaining. No clock is compared with another, no skew constant exists, and no synchronization service or configuration was added. The exchange frame names the same anchor and carries no time value, so there is nothing to renew: the server keeps the bound it retained since preparation and refuses a frame naming a different mode or anchor, claiming standalone use after a bound was prepared, or carrying a bound after standalone preparation.

Legacy frames are refused, not downgraded. The prepare frame must carry exactly binding, grant_digest, attempt_digest and primary_bound; the exchange frame exactly grant, work_packet, source and primary_bound. An explicit primary_bound: null is deliberate standalone use and keeps the grant timer alone. An older client's frame - the revision that sent lifetime_seconds, the one that sent primary_cutoff, or one with no bound key at all - is refused before preparation instead of being treated as standalone, as is a bound naming an anchor this server did not issue (which is what a client that did not wait for the anchor would send), a non-finite, non-positive or already spent value, or one above the task grant's own timeout_seconds ceiling (2700 seconds, read from TeamGrant rather than restated) - which no director holding a valid grant can send, so it is refused as malformed rather than clamped. The server's own anchor, and the resulting instant, must be finite or the frame is refused too.

Support is acknowledged before private source. The anchor frame is the acknowledgment: a server that does not speak this protocol never sends it, so the director - which waits for it before sending even the public preparation - either refuses at the first frame of the wrong kind or shape, or is ended by its own local timer at the bound having sent nothing but the challenge. In either case no preparation and no source reaches such a server. The shipped SSH client always carries a bound: the primary lane's remaining budget when one exists, otherwise its own grant timer, so the remote worker is never bounded later than the local SSH kill.

What this does not prove, stated rather than implied: killing the local SSH process bounds this side only; a server that never anchors is ended by that local timer only when the bound elapses, not sooner; preexec_fn runs between fork and exec and cannot be interrupted once Popen is entered; and cleanup spends its own five second process wait plus a further five second cgroup drain, which the transported bound does not cover. Remote cgroup teardown is not demonstrated here.

Inside the worker, the remaining budget is spent as it is: a fractional remainder stays fractional, and a non-positive one is refused instead of being rounded up into a fresh second. Preparation carries the same anchored bound through qualification, the native state scan and the durable claim, re-checked between them and once more after the claim is durable: preparation that has run out writes no claim, and one that runs out while writing it - during fsync - acknowledges nothing. That consumed claim is deliberately retained rather than deleted as a rollback: removing it would make the same qualification receipt spendable again, whereas an unacknowledged preparation leaves the exchange with no preparation and a repeat on the same receipt refused by the existing claim. serve re-checks the bound again before sending prepared. The worker also retains the bound it was acknowledged under, bound to the same attempt and challenge, and the exchange can only narrow it - a caller carrying a later bound, or none, at exchange still runs under the prepared one. run_unprivileged is unchanged from the previous revision, which an independent probe confirmed: it takes the absolute bound rather than a duration, the prompt is serialized before it, the bound is checked after cgroup and file setup and again immediately before Popen, and the value communicate receives is what is left at that moment rather than the duration the caller computed earlier; a Popen that returns after the budget has elapsed gets no wait at all, and the group is still killed and drained. Candidate integration receives the same fixed completion bound through its Git and database work rather than starting a sixty-second timer of its own.

The ordinary command boundary

The three ordinary command transports - NativeCommandPacketTransport (Claude stdin, Cursor argument, Grok prompt file, Antigravity closed directive, Copilot argument, as discover_local_primary_command_transports selects them), PublicSearchCommandTransport (both Perplexity and Firecrawl argv routes) and the explicit BoundedJsonCommandTransport - previously handed subprocess.run the full relative timeout regardless of the carried context.deadline. An independent synthetic probe at the C15 head reached the spawn with timeout=30 for a carried bound already expired and for one with 0.2 seconds left, on every one of those routes. They now share one boundary. _command_cutoff fixes one finite absolute cutoff at entry: the smaller of the context's own timeout and the transport's configured maximum, narrowed by the carried deadline when one exists; a carried bound that is not a finite number is refused, and one already spent refuses before anything is prepared. Prompt construction, the Grok prompt file, the stdin file and the spawn are all charged to that cutoff. Since 22:30 UTC the prepared input travels the way the artifact launcher already feeds its child: written to a binary tempfile.TemporaryFile, rewound, and handed to the launch as the child's stdin, so the child reads exactly those bytes through EOF and nothing is passed to communicate(input=...) a second time; empty bytes are still a file (an immediate EOF) while the argument, prompt-file and public-search argv routes keep DEVNULL, and the helper owns and closes that file on return, refusal and launch failure alike. _run_bounded_command then holds one finite absolute cutoff and checks its remainder three times: after preparation, immediately before the launch - preparation that consumed it launches nothing; after the launch, before any wait - a launch that consumed it is ended and reported ambiguous without entering a wait; and after the child returns, before its output is accepted - a return after the cutoff, real or synthetic, is refused rather than becoming a successful attempt. A cutoff or remainder that is not a finite number is refused, and no value is clamped into a longer or fresh window. The launch goes through the existing launch_contained_process (a kill-on-close Job Object on Windows, a new session on POSIX); the wait is given only the remainder at that moment; and on every exit stop_contained_process ends whatever the tree still holds, reaps the child within its own five-second grace period rather than the spent cutoff, releases the guard - the ownership token - and only then closes the remaining streams, attempting each step even when an earlier one failed. A cleanup that cannot be verified is a raised ProcessContainmentError carrying every failure and what was observed, never a result. That ordering is a source-level ownership decision; no stream-wait failure was reproduced and none is claimed. A cutoff reached after the launch is an ambiguous outcome: the command ran, so it is neither retried nor reported as unsubmitted, and the existing classification records the one admitted attempt AMBIGUOUS with its identity and slot retained. A refusal before the launch takes the same conservative classification - the existing rule for every non-transient dispatch exception, deliberately unchanged here. The evidence-recording allowance in primary_default (completion_deadline(dispatch_deadline)) is untouched: it persists an already-started attempt's outcome after execution time is spent and grants no execution or retry. Provider identity, plan-mode restrictions, environment filtering, the exact literal argv, output caps, prompt-file removal and result normalization are as they were.

What this does not prove, stated rather than implied: on POSIX the process group is signalled, so a descendant that called setsid() itself has left that group and is not reached - no protection against that escape is claimed, and the root-only Linux lifetime test still needs its authorized lane. The signed Windows host bridge still carries no shared-deadline contract: readiness now refuses a carried PlannedProviderAttempt.deadline through HostBridgePacketTransport.preflight with unsupported-host-bridge-deadline before any host I/O, leaving the wave PENDING with paid_setup_required. send and legacy no-deadline callers are unchanged; cross-host cutoff enforcement was not added. The native Codex host still refuses unenforceable token caps, and no live provider was launched: the discovered routes are exercised with a synthetic launch, and the one real process is a local Python child.

Cancellation

director_primary_parallel_batch.kill_switch - the existing authority engage_kill_switch sets and reserve_ready already honours - is now read at both remaining authority points. Atomic admission re-reads it under the same row lock it takes, so a wave cancelled while an admission is in flight gets no attempt, spend or workload row (parallel_wave_cancelled_before_admission). Dispatch re-reads it immediately before I/O, so an attempt already admitted makes no provider call (wave_cancelled_before_dispatch) while keeping exactly the rows, slot and evidence it was admitted with. No new table, flag or approval path was added.

The deadline

execute_ready reads the bound the dispatcher publishes (readiness_deadline) before reserve_ready acquires a connection or takes a lock, so pool acquisition, the writer row, the batch advisory lock and the per-assignment FOR UPDATE waits are inside it. execute_parallel_ready reads the same bound once and passes it to its own writer acquisition, so the coordinator's work ahead of execute_ready is inside the bound too. Per-assignment readiness then establishes the selection's own deadline, clamped by both the packet's timeout and the configured transport ceiling, and every later step spends that same value: live_provider_admissions, PrimaryProviderBudgetRouting.admission, PrimaryTeamRouting.grant_for/adapter, PrimaryTaskCoordinator._task_writer (through current_/renew_/acquire_task_writer), record_work_packet_artifact, the pre-I/O cancellation read, and ProviderAdapterContext.deadline itself. send narrows a carried deadline to min(carried, this request's own window), never widens it. The shared helpers refuse an already-expired bound (DeadlineExpired) rather than converting it into a one-millisecond timeout.

bind_transaction_deadline (langgraph_postgres.py) sets statement_timeout, lock_timeout and PostgreSQL 17's transaction_timeout, all LOCAL. Per-statement timeouts alone do not bound a transaction: PostgreSQL applies statement_timeout separately to each statement and again to COMMIT, so work a deferred constraint trigger performs during COMMIT gets a fresh window. transaction_timeout bounds the whole transaction including that commit-time work. When it fires PostgreSQL aborts the transaction and terminates the session, and the pool discards that connection - the test log shows exactly that discard. Every unbounded caller is unchanged: the parameter is optional throughout.

Binding happens inside an explicit transaction, never beside one. These pools are autocommit, so SET LOCAL issued outside a transaction block lasts only for the statement that sets it: an independent probe on 17.11 read both timeouts back as 0 immediately after binding, and a 0.35s sleep then completed against a 0.20s bound. A pool-acquisition timeout does not bound the SQL that follows either. bounded_transaction therefore acquires, opens one transaction and binds within it; the read paths that spend a deadline - read_primary_task_projection, current_task_writer, aggregate, the wave cancellation read and the generation-boundary authority read - all use it.

Binding tightens only, and tightening is enforced. PostgreSQL 17's assign_transaction_timeout hook enables the timer only while it is inactive, so assigning a smaller value to a running transaction updates the setting and leaves the original, longer timer in force: an independent probe on 17.11 saw SHOW report 234ms while the transaction still committed a durable row at 0.312s against a 0.25s bound. The binder therefore records the earliest absolute deadline in a transaction-local setting, takes the minimum of that and any later bound, and - when the effective bound actually becomes earlier - assigns zero to deactivate the timer before re-arming it with the tightened window. A later, larger bound is observed and discarded, so no caller can extend the earliest deadline in force, and a reused pooled connection starts its next transaction clean because the recorded value reverts with the transaction.

Classification stays conservative. Only a bound already expired before any I/O raises the narrow pre-I/O hold. Anything the server timer aborts mid-transaction surfaces as an uncaught failure, which stays AMBIGUOUS, because a client cannot distinguish an aborted commit from an unacknowledged one.

Completion

Execution ending does not make recording what already happened optional. COMPLETION_ALLOWANCE_SECONDS (primary_parallel.py) defines one bounded window for that recording, and completion_deadline(deadline) derives the single absolute cutoff from the operation's own deadline. Every call in one operation computes the identical instant, so no call can renew it, and it authorises no execution, retry or eligibility.

Two things the checkpointer does are not the pool's to bound. _cursor takes the saver's own mutex before it asks for a connection, so that wait is bounded at the same object: the saver's lock is wrapped to refuse waiting past the published cutoff, and a caller refused there has taken no connection and written nothing. Once the connection is handed over it already carries one open transaction with transaction_timeout armed, so the cumulative blob and checkpoint statements, the pipeline synchronisation and the COMMIT share one absolute deadline instead of a series of independent per-statement allowances - and an aborted checkpoint leaves nothing durable to contradict the refusal.

That cutoff reaches the foreground writes the wave actually performs: record_attempt through PrimaryTaskCoordinator.record_provider_attempt and its writer resolution, the successful roster's record_result_packet_artifact including its advisory-lock wait, execute_ready's own record_result while executor.map is still waiting, and the coordinator's aggregate, record_parallel_aggregate and outcome projection write. The checkpointer acquires its own connections and mutex, so record_parallel_aggregate publishes the cutoff for its context and the saver and pool apply it to the snapshot read, the state update and the outcome read alike. No thread, queue or background writer is introduced: when the call returns, the bound is gone.

On failure the reservation and any recorded usage are retained, the attempt stays STARTED for reconciliation, and unconfirmed persistence is reported as a failure rather than a completed wave. Nothing is refunded or replayed.

Late accounting

PrimaryProviderBudgetAuthority.record_usage verifies the receipt HMAC, the admitted spend/authority/provider binding, project and response locks, and duplicate/identical/conflicting replay. It does not require the enrollment to be current; that refusal lived only in EnrolledResponseMeter._verify.

settle takes sent_at, the instant the request was actually sent. That instant is sampled inside send immediately before the generation request - after input-token counting, not before it - and meter.verify_current() is re-run at the same point, so counting that outlives the signed window stops the send instead of pricing it. The signed tariff must have covered that instant. A request legitimately admitted and sent does not stop having consumed real tokens because the window closed, or this attempt's execution budget ran out, while the provider was answering.

A reply is "complete" the moment the provider has delivered it, which is earlier than the moment this transport can return it. HTTPX ends aiter_bytes by closing the response, and closing marks the response closed before its stream cleanup is awaited, so a cleanup that hangs or raises can strand a body that already arrived in full - and was already charged for. An independent real-AsyncByteStream probe proved exactly that: both a hanging aclose and one raising ReadError refused the attempt and left no usage row. The generation response's bytes and headers are therefore recorded as they are received, and if the failure happens before parsing, those bytes are parsed on the way out.

Completeness is proved there, never assumed: an over-bound body is refused outright, a truncated or malformed one cannot parse as a single JSON object, and every existing check - terminal status, model, tier, account binding, token accounting, capture bounds - still applies afterwards. The same recovery covers the outer client's cleanup, which previously raised ambiguity even with a complete reply in hand. The operation is still refused (... exhausted after a complete provider response or ... cleanup failed after a complete provider response), never retried, and never turned into output or funding.

Settlement is therefore bounded by one absolute accounting_deadline, derived once from the operation's own deadline plus ACCOUNTING_ALLOWANCE_SECONDS, and it replaces the execution callback inside _connection rather than widening it: that callback raises the moment execution expires, which is exactly when the fact most needs recording. The same value on every call means replay cannot extend it, and it authorises no provider work and no eligibility - an expired execution still fails. Anything the provider actually completed is retained as soon as it is parsed, so a timeout while unwinding the async contexts after parsing accounts for the reply and then refuses the attempt. Without sent_at the previous current-validity gate applies unchanged, and prepare - the gate that authorises new execution - is untouched. Signature, provider-confirmed account association, model/tier/creation freshness, token accounting and every replay check are unchanged.

Limitations

  • A selection is in-process only; a restart between reservation and dispatch fails closed rather than resuming. No migration or schema change was made.
  • The enrollment registry loader is startup-only. Replacing the file on disk changes nothing in a running process; no live file-change detection is implemented or claimed. The substitution cases above replace the in-memory registry, which is what an in-process change actually looks like.
  • An authorization refusal raised after input-token counting (the expiring enrollment case) is reported by the transport as an ambiguous provider outcome, because it is raised inside the same guarded block as real transport failures. No generation request is made and nothing is metered, so this is conservative rather than wrong, but the reason code is less precise than the pre-I/O holds.
  • transaction_timeout requires PostgreSQL 17; on an older server the helper applies statement and lock timeouts only, which do not bound commit-time work. The sanctioned lane, Compose and CI all pin 17.
  • A checkpoint aborted by its own deadline is reported as a failure and reconciled by the owner, not retried here. When the transaction timer fires during pipeline synchronisation, PostgreSQL terminates the session, so the client sees a closed connection rather than SQLSTATE 25P04; that witness accepts exactly those two shapes and nothing else.
  • Provider-outcome-unknown classification is still asserted through existing tests rather than a dedicated case in this module.
  • Full CI, an independent non-author security and source review, and an exact-head reviewer verdict remain required. Nothing here is a source acceptance, merge or activation.
