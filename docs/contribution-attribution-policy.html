Contribution attribution in Git

Current rule

Owner direction, 2026-10-01: contribution-documentation, tagging and acknowledgement procedures are discontinued. Do not require custom commit trailers, mandatory contribution headers or percentage/share paperwork. Preserve normal Git Author/Committer provenance, actual provider identity and ordinary task/review evidence. Independent review, contributor/merger separation and every existing deterministic gate remain in force.

The later owner direction supersedes the older formatting and share-record instructions on this page, in bootstrap templates and in earlier guidance. It does not authorize a false producer identity, a self-review or a self-merge. Keep ordinary author and review evidence accurate.

Historical contribution tags

Existing tags and receipts acknowledge actual contributions only. Preserve them as history; do not add new contribution envelopes, Submission Tag Headers or acknowledgement ceremonies. They never authenticate provider identity or satisfy any approval, security, CI or release gate.

Commit and pull-request records

Use the actual producer's normal Git identity and describe the change, verification and unresolved limitations in the pull request. No custom Contributed-by: trailer, prescribed Sole author: header, percentage table or share_record_sha256 artifact is required by this documentation. Existing historical records remain unchanged.

Authorship versus coordination

Work produced or materially authored by a provider remains attributed to its actual producer. The acting Director does not inherit authorship through delegation, routing, coordination, QA, review, acceptance, relay, merge eligibility evaluation, or merge execution; those activities create no code authorship. The Director may not independently accept or merge code it actually materially authored. Never rewrite provider identity or record a contributor who did not contribute.

Author and reviewer independence

The owner's sole-author and provider-family eligibility decisions remain in force. Retiring percentage/share paperwork does not reclassify an author or erase maintenance contributions. Preserve actual producer and contributor evidence; do not infer authorship from the account that opened a pull request or from a shared repository Git default.

No contributor may merge that pull request, including a maintenance-only contributor. An eligible independent reviewer thoroughly reviews the exact candidate and carries the authorized merge after current CI, security checks and the mandatory merge preflight succeed. Where the runtime material-author gate is stricter than policy, preserve that gate and report its concrete refusal; documentation does not bypass it.

A real unresolved identity or independence conflict needs reconciliation from the existing Git and authenticated run records. Do not manufacture contribution percentages, retroactive receipts or a convenient author line merely to make a gate pass. A legacy tool still demanding a retired header is a compatibility defect, not renewed owner authority for the retired ceremony.

Validation

Bind review evidence to the actual target-tip base, merge base, head and tree as applicable. Use scripts/check_contribution_tags.py for its current Git-revision and event-structure checks; its historical filename does not make tagging or authorship paperwork mandatory. Preserve all exact-candidate, CI, security, budget, approval, cancellation, merge and deployment gates.

Historical guidance and later cleanup

The superseded September text remains in the immutable pre-migration Git snapshot. It is historical evidence, not current instructions. Do not rewrite old receipts or history. A separate mechanical cleanup, if needed, must preserve existing work ownership and review controls.
