Slack discussion tagging protocol

Use one existing task thread, a short searchable header and one accountable owner. Mention a verified recipient only when that recipient needs to act. Plain provider names are the default for updates and daily reports.

Codex, the acting Director and Foreman, maintains this protocol. Claude remains Director-Orchestrator completion lead and administrator #2; Cursor remains administrator #3. Apply the current appointments, briefing standard and runtime collaboration contract. This guide governs human-visible discussion; it introduces no runtime parser or new authority.

The method to use

  1. Find the existing issue, PR, work order and Slack parent thread. Reuse that thread; start a parent only for a genuinely new task.
  2. Begin the parent or a material handoff with [Director-Orchestrator] [work ID] [message kind] [state]. State one clear question, requested action or result.
  3. Name one accountable owner. Add a live mention only for an intended action, after verifying recipient identity, channel access and the route. A native app mention may dispatch work.
  4. Link the durable record and evidence; give the next checkpoint with a date and timezone. Keep detailed findings in the authorized issue/PR, with a sanitized Slack summary.
  5. Return questions and results in the originating thread. Record delivery and substantive response separately, and reconcile uncertain sends before retrying.

Discussion tags classify a message. A Slack mention routes attention or may activate an app. Git and contribution attribution follow their existing policy; these discussion labels do not reinstate retired contribution envelopes, custom trailers or acknowledgement ceremonies.

A small, consistent vocabulary

Use uppercase kind and state tags inside square brackets. Keep the project tag exactly [Director-Orchestrator]. Choose the existing work-order ID as the work tag; if none exists, use [PR-123] or [ISSUE-123]. Retain that first work tag throughout the discussion. If a work order or PR is added later, link its ID on the Source: line as an alias rather than replacing the thread's work tag or creating another task. Follow with one kind and, when useful, one actual state. Ordinary replies may omit the repeated header when the thread already supplies context.

Include the details needed to act

A parent or substantial handoff contains: action/question; durable task source; one accountable owner; actual stage/state; evidence; next checkpoint. Keep ordinary replies brief and link back to the parent instead of duplicating the whole work order.

  • Assignments: responsible session, one writer and repository/worktree scope, owned paths, deliverable, dependencies, relevant hop/revision/timeout/budget limits, cancellation or fallback conditions and acceptance evidence. Link the full authorized order rather than posting private paths or raw packets.
  • Review or merge handoffs: PR URL, branch, full head and tree, review base/target-tip base and merge base as applicable, current CI/security evidence, sole eligible reviewer, holds and exact requested action. A title or short SHA cannot bind the candidate.
  • Provider results: actual provider/product, served model if native evidence supplies it, session/run correlation and receipt. Mark a merely requested model as requested; do not turn a client's brand or prose self-description into provider identity.
  • Repairs: reproduced symptom, evidence, cause or explicit investigation gap, impact, Foreman-directed disposition, responsible writer and remaining limits. Relevant Firecrawl/Perplexity research is required for every Foreman repair case, normally at intake and always at a named checkpoint before a repair limit. Record applicable receipt reuse.
  • Questions: technical/development questions between providers first receive external context from Firecrawl or Perplexity; begin the answer with RESEARCH: queries and sources. Keep private context out of those queries. Answer process questions directly.
  • Time: give an absolute date and America/Los_Angeles checkpoint, with UTC when useful across sessions. Record evidence times in ISO 8601 UTC. Distinguish a reporting checkpoint from a completion commitment.

Use the smallest adequate summary. Link authorized issue/PR details rather than pasting raw provider output, private source, credentials, personal contact details or administrator-only findings into the wider channel.

Keep the right conversation in the right place

  • Project discussion: reuse the existing private project-director channel and one parent thread per live task. For supported tool/API replies, supply the parent's timestamp as thread_ts, not a new unrelated parent.
  • Administrator coordination: director-admin-ops is restricted to the owner and the three appointed administrators. Provider-family membership does not grant an administrator seat. Keep detailed restricted work in its authorized destination.
  • Daily pass-down: director-passdown receives one consolidated report at 23:00 America/Los_Angeles, with separately attributed Codex/Claude/Cursor contributions and exactly seven next actions. Use plain provider names. Ongoing questions and acknowledgements belong in administrator coordination or the responsible session.
  • Durable decisions and evidence: use #299 and the concerned issue/PR. Slack carries the concise linked summary. Return every provider answer, clarification or explicit blocker through its originating channel; copying a summary elsewhere does not close the original question.

Follow the thread while responsible for the task. Broadcast a thread reply to the channel only for a milestone, material blocker or decision the wider audience needs. If an urgent top-level alert is necessary, point to the same incident thread and work ID; it does not create a second assignment. A private-channel mention does not grant access or authorize inviting someone. Slack mention and access behavior.

Acknowledge and close the loop

During a known active work window, target an acknowledgement within 15 minutes. A substantive ACK says “received”, accepts the next action or names the blocker, and gives a checkpoint. For an urgent shared-work blocker, target a meaningful update within 30 minutes. Routine work uses the named assignment checkpoint; a session that is interactive or unavailable is not a daemon or a guaranteed always-on responder. These are Foreman operating targets, not new spending authority or proof of availability.

When the checkpoint passes, the Foreman checks the existing record and session once, sends one justified follow-up through the established channel, and records a blocker or the next responsible checkpoint. Escalate through Codex/Claude/Cursor within their appointments without reassigning another writer's work or inferring takeover from silence. Reuse fresh evidence and avoid unchanged polling, mass mentions, model calls merely for status or duplicate assignments.

For a transport failure, keep the recorded attempt rules: one primary attempt; one recovery only for a demonstrably temporary failure; a third only with different transport or new information. After three recorded failures, mark that route unavailable and use the configured fallback. An ambiguous paid dispatch is reconciled rather than replayed. This guide does not change the runtime's persisted idempotency or delivery-attempt contract.

Every question ends with an answer, necessary clarification or explicit blocker and tracked follow-up in its original thread. Closure identifies the accepted deliverable, actual completion stage, evidence, unresolved limits and next responsible owner. An ACK or reaction is not an independent review ACCEPT, a merge or an owner decision.

Copyable message patterns

Replace the placeholders; the examples deliberately contain no live app mentions, real task claims or executable handoffs.

Question or blocked work

[Director-Orchestrator] [EXISTING-WORK-ID] [QUESTION] [BLOCKED]
Action: Answer whether the named prerequisite is satisfied.
Source: existing issue/PR URL and authorized work order.
Owner: responsible person/provider (plain name; verify before adding a mention).
Stage/evidence: what is verified, what is missing, and the evidence link.
Next checkpoint: YYYY-MM-DD HH:MM America/Los_Angeles; UTC if useful.

Review handoff

[Director-Orchestrator] [EXISTING-WORK-ID] [REVIEW] [AWAITING_REVIEW]
Action: Review the fixed candidate; return ACCEPT, CHANGES_REQUIRED or blocker.
Owner/reviewer: one eligible non-author reviewer and its established session.
Candidate: PR URL; branch; full head; tree; review base; target tip/merge base as needed.
Evidence: exact-head CI/security results, tests and native receipt links.
Holds/limits: applicable restrictions and the bounded authorized action.
Next checkpoint: absolute date, time and timezone.

Result with explicit stage

[Director-Orchestrator] [EXISTING-WORK-ID] [UPDATE] [COMPLETED]
Result: The assigned document is written and locally validated.
Stage: implemented and tested; independent review pending.
Evidence: candidate and validation receipt links.
Owner/next action: named reviewer receives the fixed candidate at the stated checkpoint.

The result pattern closes only the stated authoring assignment, not the independent review or project. For an acknowledgement, use [ACK] Received; next action: …; checkpoint: …, or give the actual blocker. Search an existing work ID with in:#project-director "EXISTING-WORK-ID" "BLOCKED"; do not rely on an emoji, display-name alias or a new parallel channel. Slack's documented search modifiers.

Sender, receipts and maintenance

Use the provider's authenticated native identity where established. Messages sent under the Codex Director's current temporary owner-connector authorization begin exactly: “Codex Director — sent through Edward's connector with his temporary authorization.” Put this prefix on the first line and the discussion-tag header on the next line. Other providers use their own verified route or the explicitly authorized Director relay; the prefix does not grant them independent permission to use Edward's account. Preserve the actual assistant/provider author and sender separately, including when the Director relays another provider's result. The owner-connected sender does not make an assistant message an owner approval or prove a native provider bot reply. Use the maintained contact/briefing record for the current authorization and return to the verified native route after repair.

For each substantive send, retain the destination/channel, parent and reply timestamps, permalink, actual sender/app identity, assistant/provider author, work ID, source/run correlation and evidence time in the existing delivery record. Read back once to verify the expected message and intended recipient. Then distinguish delivered, acknowledged, substantive provider response and executed/accepted work. If send outcome is uncertain, search/read the existing thread before any resend; retain the failure and configured fallback when no delivery is proved.

The Foreman owns protocol upkeep and unresolved questions. Correct a misleading tag with an explicit thread correction; preserve the original evidence and avoid silently relabelling an old review or owner decision. Material decisions remain in the authorized issue/PR. Tag names and mention syntax cannot expand an assignment, grant access, change policy gates, remove a freeze or authorize merge/deployment.
