Finding 3 — the two holds, closed

Antigravity: the team mode is already built, and I was wrong about it

I said reaching Antigravity's authorized team mode "is a code and charter change to antigravity.py's contract." That was wrong — the third correction I owe on this matrix, and the most consequential in the provider's favour.

The team mode is implemented and sits behind one configuration switch, LANGGRAPH_PRIMARY_ANTIGRAVITY_TEAM_ENABLED (config.py:750, default false). Behind it: antigravity_team.py, _artifacts.py, _routing.py, _transport.py and _worker.py; team_ddl(schema) composed into _control_plane_ddl, so the schema is created by the ordinary Migrate; a director_primary_team_guard trigger enforced at the database; a TeamGrant carrying explicit writable_paths; a PinnedSshTeamWorker; the format pair ("antigravity-team-engineering-v1", "qualified-native-worker-v1") with its schema already in docs/schemas/; and a dedicated qualification canary in provider_validation_team.py described as "a dedicated synthetic canary through the actual pinned SSH engineering worker."

So Antigravity's path to real engineering work with writable paths is configuration, migration and worker authentication, not a contract rewrite:

  1. Set LANGGRAPH_PRIMARY_ANTIGRAVITY_TEAM_ENABLED=true on the candidate profile.
  2. Migrate creates the team schema and guard trigger as part of the control plane.
  3. Authenticate the pinned SSH engineering worker — antigravity_team_transport states that absent authenticated worker evidence the lane fails closed.
  4. Run the qualification canary in provider_validation_team.py.
  5. Issue a TeamGrant with explicit writable paths bounded to a partition.

Open question for the owner: does a reachable SSH worker host exist for step 3? That is the one thing the repository cannot tell me, and it decides whether this is a Thursday task or a post-Sunday one. Everything else is on the candidate already.

Microsoft 365 Copilot: reachable only through a tenant administrator

The lane was retired by #161 and is not in LANES. The blocker is transport, and it is specific: Work IQ requires a delegated work or school Entra identity with admin-consented WorkIQAgent.Ask; personal and application permissions are unsupported, and the tenant administrator must enable Work IQ. Only a successful authenticated response bound to its Microsoft request ID, body digest, conversation ID and signed token subject proves tenant enablement and licence entitlement. Environment booleans, configuration and a consumer-app installation are not evidence.

The determination the owner must make is binary: is there an M365 business or enterprise tenant with an administrator who can grant that consent? If not, the lane is not reachable at all, and the canary requirement in Finding 1 that depends on it is unreachable with it. Either way the lane must stay out of the activation binding map until a verified response exists, because the combined live signal is AND-ed across every configured binding.
