8. Review handoff — the Director's job, corrected

Correction, 2026-09-09. Earlier revisions told the owner to "request the two ACCEPT artifacts." That was wrong: docs/slack-collaboration-bus.html and review_handoff.py assign review orchestration to the Director. The Director seeks the reviewer. The accepting non-author reviewer performs an eligible authorized merge; otherwise the action stops for owner authorization.

The ordinary flow

producer authors  →  Director builds director_review_candidate/v1
                  →  Director binds a reviewer assignment and relays it on the bus
                  →  independent provider returns exactly one verdict
                        ACCEPT              → eligibility and authorization checked → accepting non-author reviewer merges
                        CHANGES_REQUIRED    → returns to author with correction notes → revise
                        SERIOUS_SAFETY_STOP → stops

Two artifacts are not interchangeable: director_review_candidate/v1 is the ordinary review handoff; director-activation-review/v1 is the control script's activation acceptance. Conflating them was a separate Director error.

ReviewCandidateArtifact requires the logical producer to appear in material_authors, a pull_number ≥ 1, exact 40-hex base and head SHAs, changed files, tests, limitations, acceptance checks, security context, and a digest over the canonical contents. A pull request must therefore exist before a valid handoff can be built. The freshness rule is absolute: review only that exact base/head pair and digest; any new commit invalidates the review and every downstream security, CI and merge evidence item.

Bus constraints: at most three delivery attempts with a stable client message ID; no raw provider output, credentials, secret-shaped values or raw private source in the relay; ordinary review-to-merge closes in at most five major orchestration actions; revision loops are capped.

A systemic CI defect that will hit any branch behind main

Recorded on the bus 2026-09-08 and confirmed as applying to this delivery's own candidate. The contribution-attribution job diffs pull_request.base.sha..head, so once main moves ahead the range includes files the branch never touched, which carry no fresh tag pair from this author. Rebase onto current main before opening the pull request. Two traps: gh run rerun replays the stored webhook payload, so re-running never sees a corrected body; and a body edit does not re-trigger CI, because on: pull_request carries no types: filter. The PR body needs bold contribution tags as its first and last visible lines — plain [[...]] is not recognized and reports the misleading "envelope lacks one matching BEGIN/END pair."
