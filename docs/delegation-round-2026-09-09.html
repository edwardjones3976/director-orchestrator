A-06 specification, pre-staged

The implementer should need no further questions. Findings already established, so they are not re-derived:

Intake (n8n/workflows/director-intake.json)

  • Outbound call to /v1/intake: generic auth type httpBearerAuth, not httpHeaderAuth. httpHeaderAuth is for custom headers such as X-API-Key; the bearer credential type takes a single token field and is the correct one for Authorization: Bearer.
  • Inbound hop: enable Webhook node authentication — Header or JWT credential. Never an inline secret in a node parameter.
  • Forward the Slack intake receipt fields required since PR #118, intact.
  • Idempotency key: the stable Slack event ID, unmodified.
  • Non-2xx from /v1/intake: set Respond to Using 'Respond to Webhook' Node and map the failure to an explicit error response with a real status code. Do not let a failure return 200.
  • Consider the Webhook node's IP allowlist and bot-ignore options.
  • Never echo raw provider output into the response body.

Status (n8n/workflows/director-status.json, new)

  • Schedule trigger polling GET /health on the profiles in play, and /v1/staging/status only while a staging app is running.
  • Diff the readiness booleans against the previous run using workflow static data; post only on change.
  • Post immediately, regardless of change, when ambiguous_effect_count > 0, the parallel kill switch is set, or health is unreachable. (Correction 2026-09-12: The rule changed in #197; it speaks when the kill switch is engaged while parallel dispatch is enabled.)
  • Target the configured Director channel variable. Never a literal channel ID in the workflow.
  • Never post secret, DSN or allowlist values.

Both: validate with python -m json.tool. Workflow JSON carries no inline contribution tag — it is a syntax-sensitive contract and is attributed through the pull request envelope instead. Document in docs/n8n-operations.html, including how the webhook is repointed between profiles.
