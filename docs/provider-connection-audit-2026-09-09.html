Variable-name correction, 21:35 UTC. This section originally named GROK_API_KEY and GROK_REPOSITORY_TRANSPORT. Neither is the API credential setting used by Settings. The primary child-environment allowlist does recognize GROK_API_KEY as a transport alias. The credential is XAI_API_KEY (config.py: grok_api_key = os.getenv("XAI_API_KEY", "")), and repository transport is computed from the GROK_CLI_* group and is required only when GROK_ALLOW_REPOSITORY_WRITE or GROK_ALLOW_REVIEW_VERDICT is true — both default false. Acting on the original instruction would have set two variables that do not configure API readiness and left the lane closed while appearing to fix it. See the Grok lane separation note.

Scope of this finding. It governs orchestrator-dispatched Grok work. A Grok session the owner launches directly is a different surface and is unaffected — the same two-surface distinction that applies to Firecrawl.

Why delegations do not get picked up — corrected 2026-09-09 21:00 UTC

The earlier version of this section was wrong, and wrong in the direction that makes a working component look broken. It stated that two Director posts on 2026-09-09 and the availability check on 2026-09-08 "all went unanswered", and concluded that the Slack identities are not autonomous listeners. That conclusion was drawn from the channel's top-level view. The threads were never opened.

They were not unanswered. Cursor replied to every one of them, in thread, within seconds:

Director post Cursor reply Latency
2026-09-09 02:58:15 PDT The agent failed to start. Please try again. 18 s
2026-09-09 09:18:23 PDT same 7 s
2026-09-09 09:23:38 PDT same 13 s

Three for three, the same message, always within seconds. That is not silence and it is not nonresponse. Cursor is wired to this channel, is receiving the mentions, and is being triggered by them; the agent process fails to start.

This inverts the practical reading:

  • The Slack bus is a live dispatch surface. The mention reaches Cursor.
  • A-18 and A-19 were never declined and never ignored. They have never started.
  • The failure is a Cursor agent-launch fault, and each reply carries a Try Again button, so the cheapest next action is an owner press, not a reassignment.
  • The nonresponse counter in the operating charter must not be advanced for these three. A launch failure is a transport fault, not a provider decision, and counting it toward "three nonresponses ⇒ mark unavailable" would retire a provider that never received the work.

Method note, recorded because the error is the reusable part. The claim was asserted from a channel listing that shows reply counts but not replies. Reply counts were visible on all three posts. The rule that follows: a nonresponse finding requires opening the thread, and a thread that shows any reply count is not evidence of silence.
