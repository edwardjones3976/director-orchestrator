Legacy supplemental spend reservations

Opening a pre-settlement ledger migrates its existing reservations atomically to legacy = 1, serialized = 0. Unknown charges continue to count at the reserved amount on their original UTC day. Serialized, non-legacy rows from any UTC day with unknown charges block admission until authoritative cost settlement or reconciliation. Legacy rows never block admission; day rollover neither releases a non-legacy hold nor erases historical exposure.

For an authoritative legacy charge, an operator can use the existing local ProviderDailySpendLedger.record_charge(provider=..., effect_key=..., actual_cost_usd=..., now=...) maintenance API against the intended ledger. Use the exact existing provider and canonical effect key, after verifying the provider's charge. This preserves the original day and legacy marker and never lowers an already recorded actual charge. Passing None records settlement without inventing a cost and retains reserved exposure. Do not fabricate a task effect or use /dispatch-reconciliation for a legacy probe without one.

They cannot be made independent of it, so the owner ruled that Director-written evidence counts only for a runtime that is exactly the release the owner reviewed. "reviewed_release": {"candidate_commit": "<40 hex>", "candidate_tree": "<40 hex>",

Exactly those three fields, each fully matching, or there is no pin. Trusted collection (2026-09-27)

The pinned evaluator computes consistency and activation-capture reports using its own code, interpreter and dependencies. No candidate Python is executed. Live collection may inspect candidate-served readbacks, but the audit's final containment prevents every check with any C input from earning points. Direct rule tests can pass 07, 12 and 17 using trusted reports; that is not a live PASS. Unavailable or invalid owner inputs, stores, signatures or snapshots never earn a PASS. Image, candidate, generation, collection-window and final deployment-state gates still apply. Check 07 also counts OWNER_DECISION_REQUIRED assignments on settled tasks as open, including when their pending dependents are correctly blocked.

The owner-installed ~/.director-scorecard/release-descriptor.json selects trusted_collection_inputs_env: the name of an evaluator environment variable injected by the owner. Its JSON value is an in-memory input bundle, never a CLI argument, report, receipt or generated file. It contains:

  • settings: all fields of the deployment's Settings, explicitly supplied without ambient defaults. Preserve original deployment paths and values.
  • environment: the complete expected Docker environment, compared exactly with inspect. This independently selects both database endpoints, the generation pin, candidate/tree, provider bindings and configuration digest.
  • mounts: owner-approved bind mounts, each with destination and source, compared with Docker inspect. The source must be accessible to the evaluator.
  • ca: an absolute evaluator-local path and its owner-pinned sha256.
  • capture_key, route_verifier_secret, owner_authority_secret: owner-injected verification material held only in memory. Optional Responses/team verifier configuration comes from the owner's evaluator environment, never the candidate environment. Existing route configuration and capture signatures must still match; absent route verification cannot attest those captures.

Both Postgres endpoints require explicit host, port, database and user, and TLS verify-full with the pinned CA. No endpoint is rewritten to a convenient host alias. The existing database_binding() checks the primary storage identity and instance against the pinned generation. Queries use read-only transactions and timeouts; consistency uses a repeatable-read snapshot. The capture store uses the existing bounded read-only reader and CaptureVerifier. Driver errors are replaced with a fixed message without their text.

SQLite is read from the verified host mount with mode=ro and backed up using sqlite3's backup API into memory. This includes committed WAL pages. The backup has a time/size limit, is checked with quick_check, and is made query-only. Neither a live database file nor its WAL is copied with docker cp. Unavailable Docker Desktop mounts, links, invalid journals, inconsistent snapshots and backup timeouts leave collection UNKNOWN. Generation verification checks original manifest paths and configuration digests separately from local artifact access; it never rewrites a manifest to host paths or reserves a journal.

Limit: rows and HMAC keys the candidate can write are not independent proof of execution or authorship. This collector proves that evaluator-owned validators accepted the observed, owner-bound stores and signed artifacts. It does not prove that a candidate with signing authority could not fabricate them. Existing CLI captures also lack executable digests; their product attestation remains UNKNOWN until the capture producer records that evidence. Collection alone does not lift that separate gate or authorize activation.

Run it

Through the owner-installed launcher, from a working directory outside the checkout (see "Install the launcher" below). The launcher takes the repository path first; every other argument goes to the scorecard unchanged:

python -I $HOME\.director-scorecard\launcher.py <repository> --candidate-sha <full-40-character-sha> --evidence-dir <explicit-evidence-folder> --output-dir <report-folder>

An ordinary direct run refuses the checkout checks. Forging the environment claims cannot produce a relied-on score: without a valid launcher receipt, the report says UNATTESTED: not produced by the owner-installed launcher; no check may be relied on, and its counts are UNATTESTED.

Install the launcher

One-time, and again whenever the owner moves the pin. Take the launcher from the reviewed evaluator commit, never from a working tree, and pin that commit:

New-Item -ItemType Directory -Force $HOME\.director-scorecard
git -C <repository> show <evaluator_sha>:scripts/scorecard-launcher.py > $HOME\.director-scorecard\launcher.py
# then set "evaluator_sha": "<evaluator_sha>" in $HOME\.director-scorecard\release-descriptor.json

The installed copy is what runs; scripts/scorecard-launcher.py in the repository is only its reviewed source.

Owner root (#287 item 34, 2026-10-02). The launcher finds .director-scorecard under the account's profile folder as the operating system records it (Windows known folder FOLDERID_Profile; POSIX pwd), never through HOME, USERPROFILE or HOMEDRIVE/HOMEPATH. A launcher, descriptor or attestation directory copied under a caller-chosen home is not the installed launcher and refuses. The launcher hands the resolved account home to the evaluator it starts (DIRECTOR_SCORECARD_OWNER_HOME); each consumer independently resolves the OS account root and checks any forwarded claim against it. The evaluator reads owner files (descriptor, CI replica key, Security index) only from that OS-resolved root. A run the launcher did not start reads no owner files and is unattested. Check the installed file's bytes against that commit (git hash-object) before trusting it.

The launcher writes a per-run receipt in the owner-controlled ~/.director-scorecard/attestations/ directory, outside the evaluator tree. It contains the pinned evaluator_sha, archived tree_id, installed launcher_sha256 and a fresh random nonce. No signing key is introduced. The child reads that receipt through the fixed owner-directory location; environment variables only select a nonce, not a trusted file path. After the child succeeds, the launcher binds the receipt to the canonical JSON report's SHA-256. Failed or incomplete launches have no valid completed receipt.

Every activation, acceptance and issue #81 evidence path must require attested: true and successful verification through the installed launcher:

python -I $HOME\.director-scorecard\launcher.py --verify-report <report-folder>\completion-scorecard.json

Exit 0 verifies origin and unchanged report content; exit 2 means UNATTESTED. The Markdown renderer also checks the completed receipt when consuming a saved report. A missing field, copied boolean, changed report, malformed receipt, changed evaluator pin or changed installed launcher fails closed. Do not use a candidate checkout's verifier as evidence. No executable activation/acceptance importer currently consumes these saved reports; the evidence handoff must include this verification. Markdown alone is not verified evidence. Verification does not replace freshness, exact-head review, CI or any activation gate; activation_authorized stays false.

This is an owner-local file attestation, not a portable signature or protection against an actor who can rewrite the owner's installation, descriptor or receipt directory. Keep those files under the same owner control as the existing descriptor. Copying a report to another host without its trusted receipt does not transfer verification. Installing this change and moving the owner's pin remain separate owner actions.

The default is offline. It produces completion-scorecard.json and completion-scorecard.html, with UNKNOWN for facts it has not observed. The human report displays no pass total until the completed launcher receipt verifies. JSON remains the authoritative machine-readable artifact; historical Markdown receipts are preserved.

Deployment profile

--deployment names a Compose project such as edge-engine-director. The Director is the one running container carrying the labels com.docker.compose.project=<project> and com.docker.compose.service=orchestrator; zero or several matches stay UNKNOWN. The inspected container must be running, carry the org.director.candidate.commit label and an immutable image ID, and publish 8080/tcp on exactly one 127.0.0.1 binding. Its host port (for example 18082) becomes the health and API base; APP_ENV (default local) is the environment /health must report. n8n and its database are the project's n8n and n8n-db services, found the same way, and every docker exec targets a container ID, never a name.

Drill-thread kinds

Each --drill-thread KIND=THREAD_TS names one owner message the operator posted to exercise one path. A drill that was not exercised stays UNKNOWN.

Kind PASS FAIL UNKNOWN
refusal-4xx complete thread, one owner input, a DIRECTOR — BLOCKED reply, no receipt, binding 404 a bound task (200) or ambiguous binding (409), or any receipt otherwise
reserved-5xx complete thread, one owner input, a BLOCKED reply, no receipt, binding 200 and the task's readback shows one task for the thread binding 409 or more than one thread task binding 404 (the reservation was not exercised), a receipt (the gateway answered 202, so the 5xx was not exercised), or otherwise

Check 03 combines refusal-4xx, reserved-5xx and transport-failure; check 09 combines duplicate-input and ambiguous-post. Any FAIL fails the check, all PASS passes it, anything else (including a kind that was not supplied) is UNKNOWN. A transport failure (the relay pointed at a closed port, step 7b of n8n operations) reaches the same n8n ambiguity branch as a 5xx but usually without a reservation, so it reads binding 404, which reserved-5xx cannot score; it is therefore its own drill. Observable outcomes overlap between kinds (a 4xx refusal and a transport failure both read 404 and BLOCKED), so each kind names a distinct operator-labelled thread and the scorecard scores the observable outcome. The scorecard cannot tell a transport failure from a refusal or a reserved 5xx, so 03's PASS says the transport failure itself is operator-attested, not observed. The drill procedures themselves are operator actions and are not automated here.

Evidence and limits

Secrets and digests (the app-token fingerprint, generation and binding pins, command-ID digests, seal and artifact hashes, rubric digests) are compared in constant time with hmac.compare_digest.

Only observations produced by the module's fixed read-only collectors in the current process can earn points. JSON containing verified: true, a copied scorecard, model prose, a declared provider name or an unverified signature never becomes authoritative. Files in the explicitly selected evidence folder are linked with SHA256 as unverified references. The scan is non-recursive, limited to 100 entries and 2 MiB per JSON/Markdown file, and skips symlinks and hidden files. A hash establishes byte identity, not truth or author identity.

Evidence includes source, observed time, expiry, digest and applicable immutable bindings. Observations expire after five minutes. Missing, stale, future-dated, wrong-head and wrong-image evidence yields UNKNOWN, never PASS, as far as the bindings above can see it. The diagnostic trusts the named local host and service; its in-process marker is not a security sandbox against arbitrary Python code, and it does not attest an uncompromised host or validate image-label supply-chain provenance.

In the retained evaluators, health counters alone can only fail 07 and 12: a reported historical hold, hold reason or ambiguous effect fails 07 even when other health fields are missing, and a false combined_live_ready fails 12. Zero counters and a true readiness flag prove nothing. Live collection overrides these evaluator results with UNKNOWN until trusted collection is available. Worker readiness is separate in 19. CI reuses state_witness.gh_checks_green, including its actual-step and required-job checks. Its temporary ledger is diagnostic and does not imply that production merge/approval composition has injected the Witness Ledger.

Check 01 observes localhost port bindings, the gateway's channel and n8n relay configuration, and reads the actual published intake version through the native workflow-history table in a read-only database transaction. It requires the supported webhook-to-request connection and the exact static Director intake URL before performing a health request to that URL's upstream from the deployment's n8n. A healthy generic alias cannot pass for a workflow pointing elsewhere. Missing version history or an unsupported/dynamic workflow cannot pass. This is configuration/routing evidence; behavioral intake and final delivery remain separate checks. Collection reads environments in memory but emits only selected booleans/counts and the public upstream environment name, never tokens, channel IDs or the full environment.

Check 02 inventories all running Docker containers, not only Compose labels, and compares app-token fingerprints in memory. It distinguishes the gateway launch command from the known API launch command, which also inherits the token without starting Socket Mode. An unclassified same-token container yields UNKNOWN. A bounded Windows process inventory examines known Python/Node/shell gateway launch signatures without exporting command lines. Unreadable process details or a host gateway requiring app-identity reconciliation yield UNKNOWN, with the verified Docker count retained. Multiple matching Docker gateways yield FAIL. This health inventory does not attest maliciously disguised processes, other machines or remote socket sessions. Container inventory is capped at 128; a changing or oversized inventory stays UNKNOWN rather than claiming completeness.

It requires complete coverage, no exclusions/deferred surfaces and no canonical findings. Native operational limitations remain in the source manifest and the report's evidence facts. It trusts the local native index, not a cryptographic attestation of an uncompromised workstation. It reads SQLite with mode=ro, closes the handle and never calls native scan finalization. Row contracts and task lifetime. Every row task_evidence_errors reads is held to three rules on both the per-task and the global path: its state's field contract from the producer, every timestamp inside its parent's lifecycle, and no later row hidden by an earlier settled one. No child row (assignment, attempt, effect, reconciliation event, delivery, status receipt, result or work packet) may predate the task's creation (task_created_at, the projection's created_at, now also read on the global path). Each Slack delivery state carries exactly PrimarySlackDelivery's fields (DELIVERY_CONTRACT): PENDING, SUPPRESSED and SUPERSEDED were never claimed, posted, acknowledged or read back; POSTING and REFUSED are claimed with no acknowledgement or Slack ts; AMBIGUOUS likewise, with up to two readbacks; ACKNOWLEDGED carries its acknowledgement and ts but no delivery; DELIVERED is the settled lifecycle. A PENDING assignment carries no reservation or completion time, an ACTIVE or AMBIGUOUS one no completion time. A reconciliation event recorded after its claim's terminal evidence (or before its effect's reservation) is an effects conflict, and the global unresolved_reconciliation counts a claim whose terminal row predates any of its events.

Retries, decisions, bindings and projection digests.
