# Provider validation harness checkpoint

This package is an incomplete activation foundation, disabled by default. It makes owner-signed LIVE_OK status alone insufficient. No live provider was called and no production database or host configuration was changed during implementation.

The bridge exposes `/v1/provider/validate` only when explicitly configured. Requests select only a registered generation and provider; commands, accounts, packet contents, costs and namespaces come from the immutable owner-provisioned generation and existing bridge configuration. Postgres admission serializes budgets and allows only one attempt per generation/provider. Ambiguous attempts retain their reservation and cannot be replayed. The dedicated schema is `director_provider_validation_v1`; checkpoint namespace is `director-provider-validation/v1`. Constructor and evidence reads never bootstrap tables.

The explicit operator CLI is `python -m director_orchestrator.provider_validation_cli bootstrap` or `validate`. Bootstrap requires DIRECTOR_PROVIDER_VALIDATION_POSTGRES_DSN, DIRECTOR_PROVIDER_VALIDATION_MANIFEST and DIRECTOR_PROVIDER_VALIDATION_OWNER_TOKEN. The manifest has exactly generation, candidate, tree, expires_at (Unix seconds, within 24 hours), budget_units and lanes. Generation is the immutable primary generation manifest SHA256; candidate/tree must match its ActivationIdentity. Each lane contains exactly binding (ProviderActivationBinding fields), configuration_digest, cost_units and work_packet. Canary work packets use the exact candidate, VALIDATION identifiers, no tools/effects, max_hops=1 and max_revisions=0.

Validation additionally requires DIRECTOR_PROVIDER_VALIDATION_BRIDGE_URL with HTTPS and the exact validation path. The bridge requires DIRECTOR_PROVIDER_VALIDATION_ENABLED=true, dedicated capture key and owner token (at least 32 characters, distinct from each other and production authentication), and DIRECTOR_PROVIDER_VALIDATION_ACCOUNT_FILES_JSON mapping provider names to pinned local account/runtime files. Runtime capture verification also requires DIRECTOR_PROVIDER_VALIDATION_GENERATION, CANDIDATE and TREE plus the dedicated database and capture key. Keep all values in the existing protected secret/configuration mechanism. Never place credentials in this document or Git.

A capture authenticates raw native output, normalized result, native session, packet, complete activation binding, candidate/tree, generation, reservation, nonce, validation fence and expiry. The bridge checks its configured executable/account-file hashes and workspace/argv/environment identity before and after execution. The cloned executor checks the dedicated durable validation fence immediately before subprocess dispatch and never consumes production writer leases. The same authenticated capture can support both activation surfaces; recording the normal ordered activation stages remains a separate owner-authorized operation.

## Explicit remaining work before activation

* Antigravity full-team SSH validation is intentionally rejected before admission. Its dedicated worker qualification and execution-capture protocol must be integrated; generic legacy JSON cannot establish that worker's readiness.
* OpenAI JSONL and configured native JSON terminal routes carry raw bytes through the real host executor. No actual authenticated provider/account run was performed. Provider-specific installed CLI envelopes and native read-only restrictions still require qualification; metadata saying no tools is not an operating-system containment proof.
* Account-file hashes bind credential material but do not independently prove subscription/account identity. The runtime pin currently covers the executable, configured argv files, adapter source and explicitly listed account/runtime files. Operators must supply the full installed runtime closure; automatic package/dependency inventory and issuer-authenticated native account readback remain unimplemented. Workspace content immutability is not established by its path.
* The optional observation hook in NativeCommandPacketTransport is not wired into the frozen production ProviderAdapterContext. The concrete validation route uses the host executor's explicit observer; direct runtime transport capture integration remains pending.
* No signed acceptance package, deployment, provider LIVE_OK record or LangGraph ownership switch is produced here. Staging ValidateProviders may call this CLI only after its own generation/image/restore gates, and must remain disabled until the missing qualification paths are completed and independently reviewed.

Focused tests use a disposable sanctioned Postgres lane and a local synthetic subprocess. These demonstrate database fencing, admission races, budget consumption, replay prevention, raw-output authentication and the production-executor reuse path. They are not native paid-provider evidence.
