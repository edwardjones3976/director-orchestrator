P0 user experience (authoritative after refinement)

Closed loop for the personal pilot:

  1. Alarm — system-scheduled via documented Android alarm APIs, with permissions and OS fallbacks; full-screen only where allowed; audible alarm and haptics; no claim of unstoppable behavior.
  2. Approved handshake — at least hold, typing, and two-step in the first working slice; other methods (sequence, QR, NFC, voice) exposed only when actually tested. Configurable AND/OR chains after capability checks.
  3. Spoken first action — on-device TTS task-specific directive after acknowledgment.
  4. Optional 5-minute starter — guided immediate starter mission.
  5. One-tap self-reported status — Started, Still working, Done, Blocked, Skip/Reschedule, with gentle or firm follow-ups only as individually authorized in profile settings.

Task state semantics (non-negotiable)

StateMeaning
AcknowledgedUser completed an implemented handshake after the alarm; not the same as started or done.
Started / Still working / Done / Blocked / SkipSelf-reported by the user; UI and logs must label these as not verified.

Crucially: acknowledgment ≠ started ≠ completed. The app must not imply verification of work performed.

P0 profile and safety (unchanged themes)

  • User-consented profile: Nudge / Steady / Command / Reveille MAX plus advanced independent controls (voice tone, authorized alarm stream volume, cycles, quiet hours, escalation).
  • Immediate safety silence always available.
  • Manual mission scheduling first; calendar import only if safely feasible with verified permissions.
  • Local persistent state; reboot and locked-screen handling; repeat rules.
  • One bounded recovery pathway; no automatic escalation of permissions or changes to consented settings.
  • Clean mobile UI; permission matrix documentation; offline/privacy and restore checks when an app exists.

Explicitly excluded from P0

  • Mandatory Mission Receipts or any proof upload requirement.
  • File inspection, camera capture for compliance, activity surveillance, or background tracking beyond alarm/mission scheduling needs.
  • Gating task start or completion on evidence review.
  • Browser-only mockups in place of a real Android app (Kotlin/Compose preferred).
  • Mixing app source with Director-Orchestrator or owner personal file trees.

May be offered later as an optional advanced module (owner-defined evidence types). When implemented, it must remain off by default and must not retroactively become required for core loop states.
