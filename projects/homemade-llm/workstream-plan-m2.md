## Methodology decisions to declare before generation

- **D-M2-1, row contract.** Every row validates against [`schemas/director-data-v1-row.schema.json`](schemas/director-data-v1-row.schema.json). The schema makes the L1 checklist unrepresentable to break: `source_provider` and `terms_tier` are required, excluded and unclear tiers are not valid values, a provider row must carry `terms_verified_at` and the matching tier and a provider source_kind, owner and repository-history rows carry `source_model: n/a`, every timestamp is a pattern-enforced UTC instant (validators do not check `format` by default), every `receipt_ref` is a relative forward-slash path or ledger key (absolute host paths are unrepresentable), `input.repository` and the target arrays follow the work-packet schema's pattern and minItems, the three D-M2-3 leak checks are recorded per row with a representable quarantine state, per-field grades carry `id` and `field` as the scorer requires, and `scrub.gitleaks_clean` and `scrub.redact_pass` are constants set to true. A row that fails validation is not written.
- **D-M2-2, task shape.** *(Input side superseded by D-M2-10 on 2026-09-28; the target side stands.)* The input was the M1 D-M1-1 shape: `objective`, `repository`, `title`, nothing else. The target is the four scored fields (`non_goals`, `constraints`, `acceptance_checks`, `evidence_requirements`). Training on the same shape the shootout scored keeps the M1 and M2 numbers comparable.
- **D-M2-3, leak wall.** Three checks, all recorded per row, before a row is written; the D-M1-0 manifests are recomputed first and the run stops if they differ, and the frozen set A and set B references are opened read-only and never modified. (1) **Source lineage:** a row whose source PR, assignment, task or work order is a held-out item, or is derived from one (a follow-up, a revision, a reconstruction), is excluded by identity regardless of wording; the validator carries the held-out source-ID list and refuses any row whose `receipt_ref` or source metadata resolves to it. (2) **Near-duplicate content:** the row's input fields and its four scored target fields are each compared with every held-out item's corresponding fields using the M1 leak-check recipe (word shingles of 8 plus any whole scored string of 4 or more words, after the scorer's normalization), not exact match alone, because rephrased content evades string matching (Yang et al. 2023, arXiv:2311.04850; Hugging Face Evaluate's split guidance). A shingle overlap above the declared threshold on any field is a leak; a match near the threshold is **quarantined** for a non-author reviewer's decision and is never silently kept or dropped. (3) **Title and objective match** after normalization, kept as the cheapest first filter. Every check writes its result and the manifests it ran against into the row's `heldout_check` block. Held-out items are never rows (O-027), and a leak found after training invalidates the run's scores.
- **D-M2-4, source mix (proposal, for the owner to set).** About 800 rows: real history that is outside both held-out sets (at most the handful that exist, PLAN.md 4.3), owner seeds that pass G-M2-4, and the balance as provider exemplars from competing-only-clause providers whose training grant is confirmed at G-M2-2 (Anthropic API, OpenAI or Codex, Cursor; Perplexity withheld), split across at least two providers so the adapter does not learn one provider's style (risk R-27). A development split (`split: dev` in the row schema) is frozen from these eligible sources before any training run and is used only for checkpoint and hyperparameter selection; held-out sets A and B are reserved for the predeclared adapter gates and never inform selection. **The split is group-wise, never row-random:** every row carries a `source_group` (the seed, source PR, assignment or work order it descends from), all perturbations, critique-and-repair variants and provider re-generations of one group sit on the same side, the dev side holds about 15 % of groups with a floor of 20 groups, and the split record reports unique `source_group` counts per side alongside row counts. The validator (M2-S1) refuses a group that appears on both sides. A row-random split is forbidden because sibling variants in training would inflate dev acceptance. No excluded-tier row, ever. The small-data literature the Director checked (Self-Instruct, LIMA, AlpaGasus) supports filtering hard and expanding what survives, but none of it measured this four-field JSON task, so the pilot is the evidence, not the papers.
- **D-M2-5, scrub.** `scripts/scan-dataset.ps1` (gitleaks) runs over the row files, and the existing `redact()` helpers run over every text field. Both must pass before the `scrub` block is written. Personal data is a stop, not a redaction.
- **D-M2-6, training recipe.** QLoRA in the pinned Unsloth image on the M1 winner at its pinned revision, thinking disabled for Qwen3 bases (D-M1-3). v0.1 trains on the first accepted cohort, v0.2 adds critique-and-repair rows for the fields v0.1 failed most, v0.3 is the tuned rerun. Checkpoints and epochs are chosen on frozen-dev field acceptance, never on training loss alone: a lower loss without a dev-acceptance gain does not justify more epochs, and response length is not a quality signal for this JSON task. **Stop rule (frozen before v0.1 starts):** (a) *baseline*: the untuned base and the base-plus-three-shot control are each scored on the frozen dev set before training, with the same graders and rubric as M1 (fixed dev grading subset of 40 groups × 4 fields, two non-author graders; about USD 0.15 per evaluation at M1's Grok rate, charged to the M2-Q1 cap); (b) *cadence*: dev evaluation at the end of every epoch, and additionally at the midpoint of epoch 1 for v0.1; (c) *selection*: the checkpoint with the highest dev joint-field acceptance is v0.n, ties to the earlier checkpoint; (d) *minimum evidence for another epoch or another 100-row cohort*: dev joint-field acceptance rises by at least 5 points over the previous evaluation, at least two of the four fields improve, and no field falls by more than 5 points; (e) *loss falls, acceptance does not*: after one full epoch with falling training loss and no dev gain per (d), training stops, the run is recorded as data-limited, and the next action is critique-and-repair rows for the weakest fields (v0.2), not more epochs; (f) Sets A and B are scored only at the predeclared gates (v0.1 at week 4 for the 45 % early warning, v0.3 for the 60 % exit) and never for checkpoint selection. Training is response-only SFT: the loss mask covers assistant tokens only, built from the base's chat template (TRL's SFT and chat-template guides; Qwen3 needs the template patched with thinking off), and a run whose mask is empty or covers prompt tokens fails closed. Before v0.1, a 20-step probe on the winning base at its pinned revision measures peak reserved VRAM against the 12 GB card; Unsloth's published 8.5 GB for 14B QLoRA is an absolute minimum, not a fit guarantee, so a probe that exceeds the card or the storage guards stops the phase at the base choice, not at the training run. Each run writes a report JSON like the M0 smoke runs (base revision, rows, steps, mask coverage, peak reserved VRAM, loss, wall time, GGUF hash). Merged Q4_K_M GGUF per version, served by LM Studio (D-002).
- **D-M2-7, scoring.** The unchanged M1 pipeline: `eval/build_inputs.py`, `eval/generate_candidates.py`, `eval/score_packets.py`, two non-author graders. The same reference manifests, candidate manifest and grade-file digests are recorded. The base model's M1 score on each set is the regression baseline. The `ifeval` and `gsm8k` regression runs use one pinned lm-evaluation-harness revision and one task config for the base and every adapter, recorded in each report; a benchmark number without that pin is not comparable and does not count toward the 3-point bar.

- **D-M2-8, paid-call window and unknown cost.** The M2 milestone window for `scripts/spend_meter.py` starts at **2026-09-28 01:34:11 UTC**, the earliest receipt labelled with the M2 purpose prefix (Director audit `C:\llm\reports\m2-spend-window-audit-20260928.md`, SHA-256 `50CE31B5…F810F0`), so no labelled M2 receipt falls outside the window; the M1 window closes at the M1 gate, 2026-09-28 02:30 UTC (D-M1-G), and a receipt in the overlap is resolved by its purpose label, never by inference. Every M2 paid call carries the purpose prefix `homemade-llm M2`. A receipt without a cost field is counted at the declared bound of USD 1.00 (`--unpriced-bound 1.00`) and reported as unknown, never as zero; the ledger figure at each stamp states known and bounded totals separately. Until the meter carries the M2 window, its M2 report is STOP and **no paid M2 generation or grading call is made**; no-cost authoring (schema, leak wall, validator, trainer) is not blocked.
