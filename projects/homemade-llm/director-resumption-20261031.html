7. Direction proposal for the owner's macro approval

In one line: since 2026-09-29 the project has built fourteen trust roots, three student pins, a loader that tolerates a host that corrupts reads, and a series of audits, proposals and holds, but no admitted training rows and no adapter. Every pilot shows the same thing: the local 4-bit 14B teacher served through LM Studio cannot write mechanically valid four-field packets at a usable rate. The data route is the problem; the trainer is not.

The Director recommends the simple path, built on the cloud decision the owner already made.

  1. Use the rented H100 for data first, with a stronger teacher. Run one bounded teacher-generation session on the H100 with a larger Apache-2.0 open-weight teacher (Qwen3-32B, or the Qwen3-235B-A22B mixture if the instance holds it) served by vLLM in bf16 or FP8, writing the four fields for the 117 admitted KEP inputs and for the licensed proposal corpora #425 already found (NumPy NEPs, Django DEPs, OpenStack Nova specs and the rest), under the same renderer, schema, mechanical checks, leak wall, custody and two-grader admission. Terms stay clean: the teacher's licence is Apache-2.0. Expected cost is a few GPU hours. This replaces the LM Studio GGUF teacher, which has produced 2 staged rows in a month.
  2. Student: the M1 winner on the H100, the 4-bit 8B as the local fallback. Train adapter v0.1 on Qwen3-14B at 40c0698 on the rented GPU, where the 11 GiB gate does not apply, and export the Q4_K_M GGUF for local serving in LM Studio, which already serves the 14B teacher on the RTX 5070. Keep the 4-bit 8B path, whose probes pass, as the fallback if the cloud route stalls.
  3. Provider outputs: decide once. (i) keep provider outputs out of training, the status quo; (ii) ask Anthropic in writing for permission for this private, non-commercial use, the route the help centre names; (iii) decide that a private local tool does not "compete" and reopen the M2-G2 provider mix, accepting the terms risk. The Director recommends (i) now with (ii) started in parallel, because written permission removes the dispute entirely.
  4. Host: custody, grading dispatch and serving only. No more training-side engineering around the read corruption. The hardware repair, and the Memtest86+ decision, stay with the owner at the owner's pace.
  5. Process: one Director, one run sheet. Replace the 25-item freeze proposal with a single run sheet of at most one page: pinned image, pinned digests with the two-read check, dataset checksums, the run, export, checksums, teardown. No new trust root until an adapter exists. Bounded orders, one writer per file, one independent reviewer, no audit-and-proposal rounds.
  6. Dates: re-baseline after the first H100 session. L1 on 2026-11-12 is not reachable. Under O-022 the date slips and the bar holds; the Director proposes dates within one week of the first session's result.
  7. Set B: decide the size for L1. Zero of 50 frozen at a required pace of 17.5 items a week is not credible. Either a 20-item prospective Set B qualifies L1 with the per-item bar unchanged and the full 50 required for L2, or L1 scores Set A plus the historical reconstructed set as a disclosed proxy.

Decisions requested from the owner. (1) Confirm the H100 route and say whether the Lambda rental exists yet. (2) Student: 14B on the H100 with the 4-bit 8B as local fallback, or stay on the 8B. (3) Teacher: a larger open-weight teacher on the H100, or keep the local 14B GGUF. (4) Provider outputs: (i), (ii) or (iii). (5) Set B size for L1. (6) Whether "take it back over" includes the data and evaluation lane the owner gave Codex on 2026-10-06, so that Codex works there only by Director assignment. (7) Clear the GitHub Actions billing lock, without which nothing merges, this record included.
